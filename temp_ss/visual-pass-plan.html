BlueSmoke · Day 12 · visual pass

What I understood, and the order I'd do it in.

Everything from the splash to Home gets a visual pass on one branch, and only then does a single PR go to stage.

What I understood

  • Nothing merges to stage until the whole journey is done. Work keeps accumulating on the branch; one PR at the end.
  • The Bumble screenshot is a layout reference only. Its colours are explicitly out of scope — we use the locked palette.
  • You want to see the plan before I write briefs, so you can redirect it before effort is spent.
Taken from the reference
  • Full-bleed coloured ground — not white, not a subtle gradient
  • Mark + wordmark stacked and centred in the upper third
  • Actions anchored to the bottom, not floated in the middle
  • A large empty middle. The space is the design
  • Full-width pill buttons, one primary, one secondary as a plain text link
  • Fine print pinned to the very bottom, links underlined
  • Back as a floating rounded square, not a nav-bar chevron
Not taken
  • The yellow. Palette is locked — #1657D0, #0E3E9A, #E8F0FE, #22C1F2
  • The black-on-light contrast model. Bumble's ground is light so its text is dark. Ours is dark, which inverts the whole relationship — see below
  • The wordmark. We don't have one drawn. Card 1 can carry the flame alone, or "BlueSmoke" set in the UI face
  • Its icon-in-button treatment. We have no icon set yet

The one decision that gates everything else

Bumble's ground is a light yellow, so it takes dark text. Our brand blue is dark. Copying the layout therefore forces a choice about which surface the whole app sits on — and it has to be made before any screen is restyled, or they get restyled twice.

B · tint ground, blue accents

My read

A is the confident one and matches the reference's boldness — the brand owns the screen. It costs more: the flame's gradient top (#22C1F2) sits on blue and loses contrast, so the mark inverts to white on these screens, and every existing component needs an on-brand variant.

B is far cheaper. #E8F0FE is already a token, existing dark-on-light components work unchanged, and the flame renders in its full gradient. It reads calmer and less distinctive.

I'd take A for ON + AU, B nowhere — but it's your call and it changes the size of this job.

Whichever you pick, it replaces GradientGround on those screens.

That component is in src/shared/ui/** — shared, additive-only by convention. I would add a new ground rather than change it, so nothing already built breaks.

The plan

Batch A exists because of a single hard lesson: restyling 20 screens before the primitives are agreed means restyling them twice.

Two things I'd flag about this shape, then do it your way.

It's against the house rule. CLAUDE.md says one task, one PR, and warns that "a 2000-line PR nobody has seen in progress is unreviewable". This will be a large diff. That's an accepted trade for not half-restyling the app on stage.

The branch name will understate it. It says brand-mark-and-splash; it will contain the whole visual pass. P0-7.0 is genuinely the right task — its four open wireframe boxes are exactly onboarding, pairing, verification and lock — so I'd keep the branch and say so in the PR body rather than churn a pushed branch.

What I need before Batch A

1 · Ground: A or B

Brand-blue ground with white content, or tint ground with blue accents. This decides how much work every later batch is, so it can't be deferred.

2 · Onboarding imagery

The carousel is three text-only cards today. Illustration? Photography? The flame alone at three scales? Or ship it typographic and skip imagery entirely — which is fastest and, with a full-bleed ground, defensible.

3 · Batch B: now or later

App icons are ~1 hour on top of the existing Pillow script. Worth it if anything goes to TestFlight; skippable if the client's logo lands first.

One boundary I'll write into every brief.

The onboarding copy is load-bearing and must not be reworded by a visual pass. Card 2 deliberately never implies the app does the locking — the firmware dead-man timer does, and that is an inviolable rule. Card 3 deliberately says the partner answers "yes or no" rather than claiming an age was verified as 18+, because nothing in our code can confirm the vendor template actually checks age. Both readings are load-bearing, both are easy to "improve" into something false.
