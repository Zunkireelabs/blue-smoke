1. `stage` is the branch everyone rebases onto, so anything wrong in it propagates to every

2. It touched **four contested shared files** — `CLAUDE.md`, `.eslintrc.js`, `src/app/navigation.tsx`,

This is the review that should have happened before the merge. It is written after the fact and
changes nothing on `stage` by itself; the fixes it recommends are separate work.

> it removes enforcement for two rules that are still live in `CLAUDE.md`.

### 🔴 F1 — The guard removal is broader than its justification

`.eslintrc.js` loses 64 lines: `no-console: 'error'` **and** the whole `no-restricted-imports`
block (Sentry, Firebase analytics/crashlytics, `*analytics*`, `*crashlytics*`, async-storage,
`react-native-fs`, mmkv, keychain, and the future logger module) for `src/features/verification/**`.

The stated rationale — Persona's SDK captures and uploads, so "there's nothing left in that subtree
for the guard to protect" — is **half true**. Raw frames and DOB are indeed gone. But two rules
survive in `CLAUDE.md`, one of them written in this same PR (`1597c05`):

- *"Never log or persist an `inquiry_id` alongside anything that could re-identify the underlying
  document or selfie."*
- Do-not list: *"Add analytics or crash reporting to the verification subtree. **Ever.**"*

Both now have **zero enforcement**. Verified empirically rather than argued — a probe file placed in
the subtree:

```ts
export function probe(inquiryId: string, userEmail: string) {
  console.log('inquiry', inquiryId, userEmail);
  return inquiryId;
}
```

`npx eslint` on it exits **0 with no violations**. The base `@react-native` config does not restore
`no-console`.

**The guard should not be restored as it was** — most of its import list guarded against a data
class we no longer hold, and reinstating it wholesale would be cargo-culting. What is needed is a
*narrower* guard sized to what actually remains: `no-console` in the subtree, plus the
analytics/crash-reporting import ban that `CLAUDE.md` still asserts. Tracked as its own brief.

### 🔴 F2 — A production build can silently verify against the Persona sandbox

`src/features/verification/personaConfig.ts`:

```ts
const environmentName = process.env.PERSONA_ENVIRONMENT ?? 'sandbox';
const environment = environmentName === 'production' ? Environment.PRODUCTION : Environment.SANDBOX;
```

Anything unset, misspelled, or lost in the build pipeline resolves to **SANDBOX**. And the value
arrives by a fragile route: `eas.json`'s `production` profile pins no environment at all, so the
value comes from EAS project-level variables inlined at bundle time by the new
`transform-inline-environment-variables` babel plugin. A release build that simply loses the
variable is indistinguishable at runtime from one configured correctly.

In Persona's sandbox, a pass is trivially forgeable (the dashboard's Simulate action). **A
production app pointed at sandbox is an age gate that anyone can walk through.**

This inverts the fail-safe principle the spec applies elsewhere: §6.2 R3 resolves DOB ambiguity to
the *younger* age precisely so ambiguity never admits a minor. Here ambiguity resolves to the
*weaker* environment.

**Not currently exploitable** — `P2-8.0` does not exist, so nothing writes `age_verified` yet. It
must close before `P2-8.0` ships. Suggested shape: require `PERSONA_ENVIRONMENT` explicitly and
throw when unset, and refuse `SANDBOX` in a release build rather than defaulting into it.

This belongs in **§6.6** as a sixth "do not guess" item — it is the same family as template
configuration and `min_age` enforcement.

### 🔴 F3 — No tests for any of the new code

The suite is still **1 suite / 1 test**. `__tests__/App.test.tsx` renders the navigator, whose
`initialRouteName` is `Home`, so `PersonaVerificationScreen` is **never mounted** by any test. The
new `__mocks__/react-native-persona.js` exists solely to stop the *existing* test crashing on

path, and all five UI states. All are pure-logic or shallow-render targets needing no device.

For contrast, `P0-2.5` landed 51 tests across 7 suites. This is a discipline regression on the
branch everyone rebases onto.

### ⚠️ F4 — `.start()` is unguarded, repeating the crash class this commit exists to fix

The `try/catch` in `PersonaVerificationScreen` wraps **only** `getPersonaConfig()`. The SDK call
sits outside it:

```ts
Inquiry.fromTemplate(config.templateId)./* … */.build().start();
```

The commit's headline fix was a hard native crash on mount caused by a native-module/interop
mismatch. If `.start()` throws synchronously for a related reason — unlinked module, interop
regression on an RN upgrade — it throws inside `useEffect` with no error boundary in the tree, which
is the same failure shape again.

Second, related: if none of `onComplete` / `onCanceled` / `onError` ever fires (modal dismissed by
the OS, native no-op), the screen is stuck on `'starting'` — an indefinite spinner with no exit,
because `started.current` blocks re-entry. There is no retry affordance and no timeout.

Both are cheap: wrap `.start()` and fall through to the existing `'error'` state; give the terminal
states a retry control. §6.4's retry/lockout policy is `P2-6.0`'s scope, not this one — this is only
about not stranding the user.

### ⚠️ F5 — A real Persona template ID is committed to `.env.example`

```
PERSONA_TEMPLATE_ID=itmpl_AW8e9aVphL2MHDmHsLFKScZsHNLPUA
```

Introduced by `d5bad2e` (PR #11, also unreviewed). Every other value in the file is a `your-*`
placeholder; the file's own header calls itself "the team's documentation for required variables."

A template ID is an identifier, not a credential, and this one is sandbox — so the direct risk is
low. The concern is the pattern: an account-linked identifier in an example file invites a
*production* template ID landing the same way later. Restore the placeholder and keep the real value
in the environment.

### ⚠️ F6 — Persona's Maven repository is added to `allprojects`

```gradle
allprojects {
    repositories {
        maven { url 'https://sdk.withpersona.com/android/releases' }
    }
}
```

Every Gradle module in the build now resolves against a third-party repository, not just the one
module that needs it. That widens the supply-chain surface for no benefit. The standard mitigation
is content filtering so the repo can only serve its own group:

```gradle
maven {
    url 'https://sdk.withpersona.com/android/releases'
    content { includeGroupByRegex 'com\\.withpersona.*' }
}
```

Minor in isolation; worth doing in a repo that carries an explicit threat model.

### ⚠️ F7 — `P0-6.0`'s ESLint guard targets a directory this commit deleted

Cross-branch finding, and it changes what Anish needs to be told.

`feature/P0-6.0-security-design` adds a guard scoped to:

```js
files: [
  'src/features/verification/**/*.{js,jsx,ts,tsx}',
  'src/native/**/*.{js,jsx,ts,tsx}',
]
```

with an audit note (its finding **F2**) arguing that guarding only the feature subtree "left the
data-carrying half unprotected."

**`src/native/` no longer exists** — `3ed7189` deleted `MLKitVerification.kt`,
`VisionVerification.swift`, and `verificationModule.ts`, and the directory is now empty of tracked
files. So the second path matches nothing, and the rationale behind it describes a data flow that no
longer occurs.

`P0-6.0` therefore needs **rebase *and* re-scope**, not just the rebase its `.eslintrc.js` /
`Info.plist` conflicts imply. Its guard and this review's F1 are the same piece of work and should
not be written twice.

## Done well — worth saying explicitly

- **`NSCameraUsageDescription` was corrected without being asked.** It previously read *"Nothing
  leaves your phone — photos are never saved or uploaded"*, which Persona makes **false**. This is
  exactly the §12.2 store-review misrepresentation class found independently during the v1.5 spec
  realignment, caught here in the plist. A stale permission string becomes a misrepresentation to
  Apple the moment the architecture changes underneath it.
- **`onComplete` is correctly treated as a UI hint.** It sets `'pending'`, never `'verified'`, with
  inviolable rule 3 cited in the file header. This is the single most important thing to get right
  in increment 1 and it is right.
- **`onError` discards the vendor error object**, so no Persona decline reason can leak into UI —
  matching the "coaching, never diagnostic" rule.
- **`inquiry_id` is never captured or logged.** The one handle we hold is not retained anywhere.
- **The babel plugin is declared as a devDependency**, avoiding the undeclared-transitive-dependency
  defect found in `P0-2.5`.
- **The Podfile change is comment-only and says so.** No silent version pinning.
- The commit message is unusually good: it explains the native-architecture root cause, names the
  stopgap as a stopgap, and records that build artifacts were inspected rather than trusted.
