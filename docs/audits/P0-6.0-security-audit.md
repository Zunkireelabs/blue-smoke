## Why this audit exists

`TODO-phase-0.md` shows P0-6.0 at **0 / 10**. That number is misleading: §8 already contains a
four-class data table, a ten-threat model, a key-rotation strategy, three accepted residual risks,
and a compliance posture. Most of the design is written.

So P0-6.0 is not "write the security model." It is two different jobs:

1. **Verify the written model is actually true** — that §8 matches the code that now exists, and the
   native configuration that now exists. §8 was written before `P0-4.0` landed any code.
2. **Author what is genuinely absent**, and say plainly which boxes cannot be closed by writing.

The distinction matters because a security box is worth nothing if it was ticked by reading. §8.1
says 🔴 data is "RAM only, zeroised in a `finally` block." The scaffold that landed in `P0-4.0`
contains a bridge signature that **cannot satisfy that sentence** — and nothing caught it, because
§8 and the code were never read against each other.

This follows the precedent of [`P0-1.0-consistency-audit.md`](P0-1.0-consistency-audit.md): the
normative sections were internally consistent and still wrong.

## F1 🔴 — The DOB crosses the native bridge as a JavaScript string, which cannot be zeroised

**Evidence.** `src/native/verificationModule.ts:12`:

```ts
export interface OcrResult {
  dateOfBirth: string | null;   // ← 🔴 data, as an immutable JS string
  confidence: number;
}
```

**Why this is a defect.** §8.1 classifies DOB as 🔴 **never persisted** — "RAM only, zeroised in a
`finally` block." §6.1 stage 7 is more explicit: "overwrite + release all image buffers, embeddings,
DOB, and any derived strings." CLAUDE.md repeats it as a code convention.

**None of that is implementable for a JavaScript string.** Strings in JS are immutable and
garbage-collected. There is no API to overwrite one. `dob = null` in a `finally` block drops a
*reference*; the character data stays in the JS heap until GC runs, and Hermes may relocate or
copy it during compaction in the meantime. The lifetime is not ours to control.

Note what is *right* here, because it makes the gap precise: every other 🔴 value on this interface
is a `Uint8Array` — `idImage`, `selfieImage`, `selfieFrames`. Those are `ArrayBuffer`-backed and
**genuinely zeroisable** with `.fill(0)`. Whoever wrote this interface got the images correct. The
DOB is the single value that escapes as an unzeroisable type.

**Blast radius.** `P2-2.0` (OCR + DOB extraction, 4.8 d) and `P2-3.0` (age computation, 2.0 d) are
both specified to consume this shape. Deciding after they are built is a rewrite of 6.8 person-days
of work; deciding now costs a conversation.

**Options, with honest costs:**

| | Approach | Cost |
|---|---|---|
| **A** *(recommended)* | Native computes the age gate. Bridge returns `{ meetsMinAge: boolean, confidence }` and the DOB never enters JS at all. | §6.2's R1–R7 normalisation rules must be implemented **twice** — Swift and Kotlin — against §9.2's "one shared TS interface" intent. Two implementations of R3's fail-safe-to-younger rule is a real correctness risk. |
| **B** | Bridge returns `dateOfBirthBytes: Uint8Array`. R1–R7 stay shared in TS, and the buffer is zeroisable. | Parsing to compare dates still materialises integers (y/m/d) that cannot be zeroised. Better than a string, not clean. |
| **C** | Accept as a documented residual risk under §8.5. | Contradicts a stated inviolable rule. If we choose this, the rule's wording must change — an unenforceable rule is worse than an honest limitation. |

**This is not mine to decide unilaterally** — it changes §6 and Phase 2 scope, and Sadin owns the
spec. Raising it as the first agenda item for the P0-6.0 team session (see box 3 below).

## F2 ⚠️ — The 🔴-zone ESLint guard does not cover `src/native/**`

**Evidence.** `.eslintrc.js:11` scopes the override to:

```js
files: ['src/features/verification/**/*.{js,jsx,ts,tsx}']
```

But CLAUDE.md's own codebase map defines the Verification area as **`src/features/verification/**`
*and* `src/native/**`** — and `src/native/verificationModule.ts` is precisely where raw ID images
and the DOB cross the bridge.

**Consequence.** `src/native/verificationModule.ts` may today import a logger, `react-native-fs`,
or Sentry, and `npm run lint` passes. The guard protects the subtree that holds the *orchestration*
and leaves unprotected the subtree that holds the *data*.

**Fix** — extend the glob. One line, in this branch.

## F3 ⚠️ — The guard blocks persistence and logging, but not transmission

**Evidence.** Inviolable rule 1 forbids three things: 🔴 data "written to disk, **logged**, sent to
a crash reporter, or **transmitted**." The ESLint override blocks storage modules (`async-storage`,
`react-native-fs`, `react-native-mmkv`, `react-native-keychain`), loggers, and analytics/crash
packages. It blocks nothing that transmits:

- `@supabase/supabase-js` is a dependency and is **not** on the restricted list
- global `fetch` and `XMLHttpRequest` are unrestricted

**Consequence.** The one-third of rule 1 with the worst failure mode — an ID image leaving the
device — is the third with no automated guard. Rules 1 and 2 are enforced by tooling; rule 3 is
enforced by hoping nobody types `fetch`.

**Fix** — add `@supabase/supabase-js` to restricted paths, and `no-restricted-globals` for `fetch`
and `XMLHttpRequest`, in both verification subtrees.

## F4 ⚠️ — Box 8 says "TLS 1.3 enforced." minSdk 24 makes that impossible on Android

**Evidence.** `android/build.gradle:4` sets `minSdkVersion = 24`. Android's platform TLS provider
supports **TLS 1.3 only from API 29** (Android 10). On API 24–28 the app negotiates TLS 1.2 —
regardless of what the box claims — unless a provider is bundled.

iOS is fine: TLS 1.3 from iOS 12.2, well below any target.

**What is already correct, and should be credited:**
- `NSAllowsArbitraryLoads` is `false` (`Info.plist:33`) — no cleartext on iOS
- `targetSdkVersion = 36`, so Android's `usesCleartextTraffic` defaults to `false`

**Two sub-items still open:**
- `NSAllowsLocalNetworking` is `true` (`Info.plist:35`). That is the React Native template default,
  needed for the Metro dev server. It permits local-network cleartext and should be **Debug-only**,
  not in a Release build.
- Android's cleartext posture is *implicit* in the targetSdk default. Make it explicit with
  `android:usesCleartextTraffic="false"`, so lowering targetSdk later cannot silently re-enable it.

**Decision needed:** raise minSdk to 29, bundle Conscrypt, or restate the box as "TLS 1.2 minimum,
1.3 preferred where the platform provides it." Raising minSdk drops Android 7–9 devices, which is a
product call, not a security one. **Certificate pinning is not proposed** — with Supabase as the
only origin and no pin-rotation process on a 30-day timeline, a stale pin bricks the app for every
user. Recommend documenting that as a deliberate decision rather than an omission.

## F5 ⚠️ — An empty permission purpose string, for a permission the app never uses

**Evidence.** `ios/BlueSmoke/Info.plist:41-42`:

```xml
<key>NSLocationWhenInUseUsageDescription</key>
<string></string>
```

A `grep` for `location` across `src/` returns nothing. No code requests location.

**Two problems.** An empty purpose string is an App Store review rejection risk — Apple requires a
non-empty, specific reason for any declared permission. And declaring a permission the app does not
need directly contradicts §8.6's data-minimisation posture: this is a privacy claim we make to the
user and to review, and it is currently false.

Contrast with the Bluetooth and camera strings on lines 38 and 40, which are specific, honest, and
explain the privacy guarantee to the user. Those are good. This one is an unedited template
artifact sitting next to them.

**Fix — delete the key entirely.** iOS BLE central operation does not require location.

**Credit where due:** the *Android* permission set is exactly right and clearly deliberate —
`ACCESS_FINE_LOCATION` is capped at `maxSdkVersion="30"` and `BLUETOOTH_SCAN` carries
`usesPermissionFlags="neverForLocation"`, which is the correct API-31+ posture and the thing most
BLE apps get wrong. The iOS side just wasn't given the same pass.

## F6 ⚠️ — §8.3 has no threat for the OS writing our 🔴 data to disk

**Evidence.** §8.3's ten threats cover BLE sniffing, replay, relay, stolen phone, rooted device,
minor-with-adult-ID, printed-photo spoof, client flag tampering, firmware key compromise, and
command flooding. All are threats to *the protocol* or *our code*.

**The missing threat is the platform itself.** When an app backgrounds, both iOS and Android
capture a snapshot of the foreground window and **write it to disk** for the app-switcher preview.
If that happens while the ID or the selfie is on screen, the operating system persists an image of
a government ID to disk — breaching inviolable rule 1 completely, with our code behaving perfectly.
The user pressing the home button is enough. Screenshots and screen recording are the same class.

This is the most likely real-world breach of rule 1 in the entire product, and it is the one threat
no amount of `finally`-block discipline prevents.

**Mitigations** (design-level here; implementation belongs to `P2-1.0`/`P2-4.0`):
- **Android:** `FLAG_SECURE` on the capture and selfie screens — blocks both the snapshot and
  screenshots at the window level.
- **iOS:** no `FLAG_SECURE` equivalent. Cover the preview with an opaque overlay on
  `applicationWillResignActive`, before the snapshot is taken.
- **Both:** scope this to the capture screens only, not app-wide — `FLAG_SECURE` on the whole app
  breaks legitimate screenshotting of, say, a device-pairing error the user wants to send support.

**Also worth a line in the zeroisation policy:** a *native* crash inside the Swift or Kotlin ML
bridge can produce an OS-level crash log containing heap memory, and Xcode Organizer plus Play
Console collect those by default. The ESLint rule stops *us* importing a crash reporter; it does
nothing about the platform's own. This needs stating even though the answer is partly "accepted."

## Proposed eleventh box — the test-set handling policy

The labelled face-match set (§6.3: ≥ 40 genuine ID + selfie pairs, plus cross-pairs) is **the one
place this project deliberately retains 🔴 data**. Every other 🔴 value is RAM-only by rule. The
test set is real government IDs and real faces, belonging to real people, kept on disk for weeks.

`.gitignore` already blocks it from the repo — `test-data/ids/`, `test-data/selfies/`,
`test-data/faces/`, `fixtures/verification/`, tagged with a §8.1 reference. Someone thought about
this, and it is the right first control.

But .gitignore answers only "not in git." It does not answer: who consents, and in what form; where
the files may live; encrypted at rest or not; who may access them; when they are destroyed; and
what happens to them at project end. None of that is written anywhere.

P0-6.0 owns the data-handling model and the same person is collecting the set, so the policy
belongs here rather than in P2-5.0 where the tuning happens.
