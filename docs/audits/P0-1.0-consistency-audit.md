# P0-1.0 — Architecture Consistency Audit

**Date:** 2026-08-05 · **Auditor:** tech lead · **Branch:** `feature/P0-1.0-architecture-signoff`
**Subject:** `TECHNICAL_SPEC.md` §2 (architecture) cross-checked against §3–§9

---

## Why this audit exists

`TECHNICAL_SPEC.md` is ~65 KB written in a single pass. It describes **one system from several
angles**: §2 narrates it, §4 specifies the wire protocol, §5 specifies the database and server,
§8 specifies the security model, §9 specifies the app.

Angles written in one pass drift. The normative sections get revised as detail firms up; the
narrative section that summarised them does not. Nobody notices, because the narrative reads
correctly on its own.

That matters here because **§2 is the section people read first.** A developer starting a task
skims the data flows, not the byte layouts. If §2 disagrees with §4, the code follows §2 and
fails at integration — months after the divergence was introduced.

```
                        §2  ← everyone reads this first
                         │
        ┌────────┬───────┼────────┬────────┐
        ▼        ▼       ▼        ▼        ▼
       §3       §4      §5       §8       §9   ← normative detail, kept current
     hardware  wire    server  security   app
        
     the audit asks, for each pair: do these still say the same thing?
```

Ticking P0-1.0's boxes asserts the design is sound. This is the work behind that assertion.

## 🔴 Finding 1 — Flow B derived the session key wrongly *(critical)*

**Severity: critical.** This would have produced a system that fails 100% of unlocks on real
hardware, discovered at Day-26 integration.

`§2.3 Flow B` and `§4.5`/`§5.4` disagreed on the **HKDF parameters**:

```
  §2.3 Flow B  (as written)
      K_sess = HKDF( K_dev, "bluesmoke-session-v1" | user_id | session_id )
                             └──────────── all of this as INFO ────────────┘
                                                            ▲
                                              session_id used here

  §4.5 + §5.4 + §5.2.6  (agreeing with each other)
      K_sess = HKDF( ikm  = K_dev,
                     salt = session_id,        ◄── session_id is the SALT
                     info = "bluesmoke-session-v1" | user_id | expires_at )
                                                                 ▲
                                                    expires_at, not session_id
```

Two independent errors: `session_id` placed in `info` rather than `salt`, and `expires_at`
replaced by `session_id`.

**Why it would have been fatal.** HKDF with different salt/info produces a completely different
key. The server derives `K_sess` one way and hands it to the phone; the device re-derives it
independently from `K_dev`. If the two derivations disagree by even one byte, **every CMAC
comparison fails** — and §4.5 mandates constant-time comparison, so there is no diagnostic
signal. It presents as "authentication always fails, no reason given."

**Corroboration.** `§5.2.6` comments the `session_id` column as *"the 16-byte salt used in HKDF"*.
Three sections agreed; §2.3 was the lone outlier.

**Corrected:** §2.3 Flow B now matches §4.5/§5.4 exactly, with inline markers on both parameters.

## ⚠️ Finding 2 — Flow B's request and response fields were wrong

Smaller, same cause.

| | §2.3 Flow B (as written) | §5.4 (normative) |
|---|---|---|
| Request field | `device_serial_hash` | `serial_hash` |
| Request field | *(absent)* | `requested_ttl_days` |
| Response field | *(absent)* | `key_generation` |

`key_generation` is not cosmetic — §8.4 makes it the mechanism by which a fleet carries mixed key
generations without an app update. A client built from Flow B would not read it.

**Corrected:** field names aligned, both missing fields added.

## ⚠️ Finding 3 — Flow C understated the handshake

```
  §2.3 Flow C  (as written)
      proof = CMAC(K_sess, 0x01 | protoVer | N | session_id )
                                                 └── all 16 bytes ──┘
      → write authResponse                       ← implies ONE write

  §4.5  (normative)
      proof = CMAC(K_sess, 0x01 | protoVer | N | session_id[0..3] )
                                                 └── first 4 bytes ──┘
      → TWO ordered frames; out-of-order resets the handshake
```

Two divergences:

1. **CMAC input length.** 16 bytes of `session_id` versus 4. Different input, different proof,
   authentication fails — same failure mode as Finding 1.
2. **Single vs. two-frame write.** §4.5 requires two ordered writes to stay inside the 20-byte ATT
   payload, and mandates that frame order is enforced. Flow C showed one write, so an implementer
   working from it would not know the ordering requirement existed.

**Corrected:** both, with the `[0..3]` truncation and the mandatory frame ordering marked inline.

## ⚠️ Finding 4 — §2.2 trust boundaries were incomplete

The boundary table understated two crossings:

**Verification engine → rest of app.** Listed three fields; §9.2 rule 2 and §5.2.2 both specify
**four**. `outcomeReason` was missing.

**App → Supabase.** Listed `age_verified`, timestamp, method, serial hash. `§5.2.2` also stores
`threshold_version`, `outcome_reason`, `app_version`, and `platform`.

**The part worth attention:** `outcome_reason` can be `under_18`, and it *does* cross to the
server. That is a derived age fact. It is not a date of birth and it must never become one — but
§2.2, the section people consult to answer "may this cross?", did not mention it at all.

**Corrected:** both rows completed, `similarity score` added to the never-cross column, and a note
added fixing `outcome_reason` as deliberately coarse:

> *It records that a check failed, never by how much and never the underlying date. Keep it
> coarse: adding granularity here would turn a support signal into stored personal data.*

## ✅ Check 4 — RAM and payload budget: consistent

§3.1 requires every GATT payload ≤ 20 bytes, fixed-size, no fragmentation — the 8 KB RAM budget
is shared with the BLE stack.

```
  ATT MTU 23 bytes − 3 bytes ATT header = 20 bytes usable

  C1 deviceInfo     20  ██████████████████████  ← at the limit
  C2 authChallenge  16  ██████████████████
  C3 authResponse   20  ██████████████████████  ← at the limit
  C4 lockState       8  █████████
  C5 lockCommand    20  ██████████████████████  ← at the limit
  C6 commandResult   4  ████
                        └──────────────────┴ 20 B ceiling
```

All six within budget; three sit exactly at it. **Consistent — no change.**

> **Standing constraint:** three characteristics have zero headroom. Any future field added to
> `deviceInfo`, `authResponse`, or `lockCommand` forces either fragmentation or an MTU exchange,
> both of which §3.1 rules out. This is a hard ceiling, not a soft one — flagged for whoever
> proposes a `protocolVersion 0x02`.

## ✅ Check 5 — Key hierarchy vs. schema and rotation: consistent

The concern: OTP is write-once, so any rotation story assuming `K_dev` can be rewritten is fiction.

```
  K_dev ──► burned once into OTP at manufacture.  CANNOT be changed in the field.
    │
    ├─► §5.2.5 device_keys.k_dev_wrapped   — server copy, Vault-encrypted, RLS deny-all
    ├─► §5.2.3 devices.key_generation      — lets a fleet carry mixed generations
    │
    └─► K_sess = derived per activation, expires ≤ 90 days, revocable
                 └─► §8.4's actual day-to-day rotation mechanism
```

§8.4 does **not** claim OTP is rewritable. It rotates what it can — session keys, continuously —
and handles hardware-level rotation by generation on future revisions. `§5.2.5` and `§5.2.3` both
carry `key_generation`, so the schema supports it.

**Coherent — no change.** The rotation story is honest about the constraint.
