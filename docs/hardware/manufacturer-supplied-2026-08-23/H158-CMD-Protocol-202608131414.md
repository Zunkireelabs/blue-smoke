## 1. 数据格式 / Data format

**SDK → Terminal** (no ACK byte)

| | head | length | CMD | Data | checksum | Tail |
|---|---|---|---|---|---|---|
| 长度 / Size | 1B | 1B | 1B | XX | 1B | 1B |
| 值 / Value | `02` | `xx` | | VAR | | `01` |

**Terminal → SDK** (adds an ACK byte)

| | head | length | CMD | ACK | Data | checksum | Tail |
|---|---|---|---|---|---|---|---|
| 长度 / Size | 1B | 1B | 1B | 1B | XX | 1B | 1B |
| 值 / Value | `02` | `xx` | | | VAR | | `01` |

**Check sum 的计算方式：从 head 字段 到 data 字段，所有的数据异或的结果。**

> **EN:** Checksum is the XOR of every byte from the `head` field through the `data` field.

## 2. 指令说明 / Command reference

### 2.1 童锁设置 / Child lock

**SDK →**

| CMD (1B) | Data (1B) |
|---|---|
| `A1` | `78` / `87` |

- `0x78`：加锁 / **lock**
- `0x87`：解锁 / **unlock**

**Terminal →**

| CMD (1B) | ACK | Data (1B) |
|---|---|---|
| `A1` | `00` / `x0` | `78` / `87` |

**ACK 为 00 时，表示处理成功，数据域内容为当前状态。**

> **EN:** When ACK is `00` the command succeeded, and the data field carries the *current state*.

### 2.2 终端信息 / Terminal information

**SDK →**

| CMD (1B) |
|---|
| `A2` |

> Note: **no data byte.** So the frame is `02 01 A2 A1 01` — length `0x01` (CMD only).

**Terminal →**

| CMD (1B) | ACK | Data (3B) |
|---|---|---|
| `A2` | `00` / `x0` | |

**Data field:**

| | Value (hex) | explanation |
|---|---|---|
| B1 | `31` / `30` | 童锁状态 / child-lock state — `31` 锁定 locked, `30` 解锁 unlocked |
| B2 | `00`–`03` | 系统开关机状态 / system power state — `00` 开机 power-on, `01` 关机 power-off, `02` 预热 preheating, `03` 加热 heating |
| B3 | `00`–`64` | 电池电量百分比 / battery charge percentage |

## What this document does *not* contain

The table of contents lists **only** sections 1 (data format), 2 (commands), 2.1 (child lock) and
2.2 (terminal information). There are **no other commands** — no firmware-version query, no separate
battery command (battery arrives in B3 of terminal information), no auth or pairing command.

This answers the 2026-08-13 reply's item 11, which deferred a request for "a complete list of the
commands the device supports" to this document. The complete list is lock, unlock, and terminal
information.

## Two places this contradicts the 2026-08-21 Q&A prose

Both resolved in favour of this document, which their own `BleProtocol.swift` agrees with:

1. The 08-21 "Device info command" table gives TX as `02 02 A1 A1 01` — CMD `0xA1`, length `0x02`.
   §2.2 above specifies CMD `0xA2` with no data byte, i.e. **`02 01 A2 A1 01`**. Their
   `BleProtocol.swift:91-93` builds `encodeFrame(cmd: 0xA2)` and `BleProtocolTests.swift:154-162`
   asserts `cmd[1] == 0x01`, `cmd[2] == 0xA2`.
2. The 08-21 "Unlock command" Terminal→App row gives checksum `0x26`, duplicated from its own TX row.
   Under §1's XOR rule the value is `0x02 ^ 0x03 ^ 0xA1 ^ 0x00 ^ 0x87` = **`0x27`**.

## ACK values not listed here

§2.1 and §2.2 write ACK as `00 / x0` without enumerating the error codes. Those come from the
2026-08-13 reply, item 12:

| ACK | Meaning |
|---|---|
| `0x00` | success |
| `0x01` | 数据错误 / data error |
| `0x02` | 数据长度错误 / data length error |
| `0xF1` | 未知命令 / unknown command |

And: an invalid frame — bad head, bad tail, or bad checksum — gets **no response at all**, not an
error frame. Only a structurally valid frame with bad content produces a non-zero ACK.
