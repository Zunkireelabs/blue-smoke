## What their answers settle

1. **`0x81` / `0x82` is not a new protocol.** It is the *old* firmware replying to
   a *newer* app. Confirmed by their own source: the exact string Anish saw on
   2026-08-20 — `Failed to parse BLE frame: Invalid frame head: 0x81` — is
   generated by `BleProtocol.decodeFrame`'s `bytes[0] == 0x02` guard in
   `H158_IOS/h158lib/h158lib/Protocol/BleProtocol.swift`. Fix is the firmware
   upgrade, not a decoder for `0x81`.
2. **Response framing, which we previously did not have.** Commands are
   `HEAD LEN CMD DATA CHECKSUM TAIL`; responses insert an **ACK byte** after CMD:
   `HEAD LEN CMD ACK DATA CHECKSUM TAIL`, `ACK 0x00` = success. Checksum is XOR
   over every byte from HEAD up to the end of DATA. See `BleProtocol.swift`.
3. **`deviceInfo` data field is 3 bytes** — `[lockState, systemState, battery]`,
   where systemState is `00` power-on / `01` power-off / `02` preheating /
   `03` heating, and battery is a hex byte read as decimal (`0x64` = 100).
4. **Advertising is 10 minutes after a button press** — but *only* on
   `_260814_01_`. Also new: after a connect-then-disconnect, advertising stays up
   for **3 minutes**. This explains the few-seconds window observed on the older
   image on 2026-08-20.
5. **The chip-identity discrepancy is a non-issue.** PY32F002B and PY32C642 are
   the same die, different package marking.

## What this confirms in our codebase

- `src/features/ble/hqdFrame.ts` inferred the frame structure from three sample
  frames and flagged the structure as inference. **The inference is correct** —
  their `BleProtocol.swift` implements exactly it: same STX/ETX, same XOR
  checksum, same `0xA1`/`0xA2` commands, same `0x78`/`0x87` lock args.
- `protocol.ts` `YP65_PROVISIONAL.dataPipe: 'fff1'` was recorded as a guess to be
  settled on hardware. **Their `BleSdkConfig.swift` settles it**: a source comment
  states the UUIDs were measured with LightBlue — service `0xFFF0`, and *both*
  read and write go through `0xFFF1`.

## ⚠️ Two encodings for "locked" — do not conflate

The lock/unlock **command argument** and the deviceInfo **response byte** use
different values for the same concept. Both are in their source as separate
constants:

| Meaning | Lock/unlock command arg | deviceInfo response byte 0 |
|---|---|---|
| Locked | `0x78` (`childLockLocked`) | `0x31` (`termInfoLocked`) |
| Unlocked | `0x87` (`childLockUnlocked`) | `0x30` |
