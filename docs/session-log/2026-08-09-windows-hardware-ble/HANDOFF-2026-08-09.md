## 3. Design decisions to preserve when you re-skin

1. **Discovery and connection are separate modules.** Discovery ends at "what's in range";
   `connection.ts` owns the link. That's what lets a pairing screen and a connection screen each
   own their own state.
2. **Scanning is a separate interface (`BleScannerLike`), not more members on `BleManagerLike`.**
   Widening `BleManagerLike` breaks every hand-rolled fake manager literal implementing it — 11 in
   `auth.test.ts` alone (that ripple already happened once when `onDeviceDisconnected` was added).
3. **Never show lock state on a connection screen** (§7.1). The firmware dead-man timer is the
   safety authority; a "connected" badge is not. Reconnect only makes relock *feel* fast.
4. **Everything is injected** — no module imports `react-native-ble-plx` or a mock by name. When
   real firmware exists you swap the manager at one seam.
5. **Every BLE op has an explicit timeout**; nothing throws a raw transport error across a public
   boundary (typed outcomes, mirroring `auth.ts`).

## 4. Deliberately NOT simulated (don't "fix" these)

- **§4.5 handshake.** Needs a `K_sess` only `issue-device-session` can mint → blocked on **OQ-12**
  (the `serial_hash` salt). An "authenticated ✓" badge backed by an invented key would prove
  nothing. It stays proven in `auth.test.ts` against the Node mock's *independent* crypto.
- **Bonding / LESC.** OS-level, cannot be faked in-process.
- **Lock/unlock (`commands.ts`, P3-2.0)** and **proximity (`proximity.ts`, P3-3.0)** — still stubs
  that throw their task id.

## 5. Hardware investigation (full detail in `temp_ss/hardware-findings.md`)

The client's `C:\Users\USER\Desktop\BlE-device` drop + hands-on with the single PCBA + PW200:

- 🔴 **Two-chip design.** App MCU **PY32F002B / PY32C642F** (24 KB flash, 3 KB SRAM, **128-byte
  OTP**) + a **separate Yichip YC1012 BLE SoC** (8 KB OTP, hardware AES128) over UART (HCI-H5/AT).
  **The GATT server lives on the YC1012, not the chip itron programs.** Our §4 assumed one chip.
- **The shipping firmware does not implement §4** — it's itron stock: a 6-digit pairing PIN plus
  read-info/set-state. So our app cannot talk to a real device until itron builds §4 firmware.
- **OQ-4 is mechanically confirmed possible**: OTP exists and PowerWriter has an OTP tab, so a
  per-device `K_dev` can be burned with the existing factory toolchain.
- **SWD debug is locked** (`[0009] target chip is not connected` even when powered) — consistent
  with production read-out protection. Not unlockable without a mass erase; we did **not** try, as
  there's only one sample.
- **BLE enumeration of the real device is blocked** — the bare board has no battery and won't run
  its radio (tried the programmer feed and a real USB charger).
- **Wrong datasheet corrected** — client sent PY32F030 (64 KB); real part is PY32F002B (24 KB). I
  downloaded the correct Puya datasheet into their `Datasheet/` folder.
- **YC1012 command manual is NOT public** (only the different YC1021 is). Must come from
  itron/Yichip — **top outstanding document**, since it decides whether custom §4 GATT is possible.
  Research on sibling parts suggests it *is* likely possible (custom 128-bit UUIDs are a documented
  family capability, and `_JD` implies a customer firmware build) — but unconfirmed.
