## 2. The contract to implement

`connection.ts` already declares the interface — keep it, extend only if needed:

```ts
type ConnectionState = 'disconnected' | 'connecting' | 'connected' | 'reconnecting';
interface ConnectionManager {
  connect(deviceId: string): Promise<void>;
  disconnect(deviceId: string): Promise<void>;
  getState(deviceId: string): ConnectionState;
  onStateChange(deviceId: string, listener: (state: ConnectionState) => void): () => void;
}
function createConnectionManager(/* inject deps */): ConnectionManager
```

Behavioural requirements:
- `connect()` → state `connecting` → on success `connected`; on failure/timeout back to
  `disconnected` (surface the failure as a typed result or rejected promise — see §4 pattern, don't
  throw raw transport errors across the boundary uncaught).
- **Involuntary disconnect** (supervision timeout / radio loss, i.e. the mock's
  `simulateAbruptDisconnect()`): transition `connected → reconnecting`, then attempt reconnect with
  **bounded exponential backoff + jitter**; on success `→ connected`, on exhaustion `→ disconnected`.
- **Voluntary `disconnect()`**: transition to `disconnected` and **do NOT auto-reconnect**. This
  distinction is the crux — an app-initiated disconnect must not fight itself with a reconnect loop.
- `getState()` returns the current state per device; `onStateChange()` registers/《unregisters》a
  listener (return an unsubscribe fn, mirror `auth.ts` subscription style).
- **Foreground/background** (§7.1): expose a way to signal app background/foreground; while
  backgrounded, suspend active reconnect attempts (iOS will suspend the app anyway) and resume on
  foreground. Keep this a simple injected signal or method — do not pull in native app-state libs.

## 3. Dependency injection & the shared file (IMPORTANT)

`createConnectionManager()` must take its BLE dependency by injection, exactly like
`createAuthHandshake(manager: BleManagerLike)` — never import `react-native-ble-plx` or the mock by
name. Inject `BleManagerLike` from `src/features/ble/BleClientContext.tsx`.

**`BleClientContext.tsx` needs an additive extension — it is a SHARED FILE (announce; append-only).**
Today `BleManagerLike` exposes `state / connectToDevice / isDeviceConnected /
cancelDeviceConnection`. It has **no way to observe an involuntary disconnect**, which this task
needs. Add — mirroring the real `react-native-ble-plx` API — a manager-level disconnect
subscription:

```ts
// ADD to BleManagerLike (do not remove/rename existing members):
onDeviceDisconnected(
  deviceId: string,
  listener: (error: Error | null, deviceId: string) => void,
): { remove(): void };
```

Then implement it on the mock's `MockBleManager` (`tools/mock-peripheral/bleAdapter.ts`) by
delegating to the existing `MockDevice.onDisconnected(...)` (already present, already fires on both
`cancelConnection()` and `simulateAbruptDisconnect()`). This is an additive change to the mock too.
Keep the real-`BleManager` default working (its real method signature matches).

Also inject a **timer/scheduler seam** for backoff delays (e.g. `wait: (ms) => Promise<void>` with a
default of real `setTimeout`), so tests drive backoff deterministically without wall-clock sleeps.
Do not use bare `setTimeout` for backoff without a seam — the mock is fully deterministic and tests
must stay so.

## 4. Patterns to follow (copy the house style from `auth.ts`)

- **Every BLE op has an explicit timeout** (CLAUDE.md hard rule). Reuse the `withTimeout` shape from
  `auth.ts` (per-stage budgets); connect/disconnect each get their own. No unbounded `await`.
- **Nothing throws across the public boundary.** `auth.ts` resolves everything to a typed
  `HandshakeOutcome`. Do the same: model connect failures as typed outcomes or a well-typed rejected
  promise, never a raw transport error escaping `connect()`.
- **Timeouts/backoff numbers are app-level, not §4 constants** — keep them `const` in `connection.ts`
  with a comment, exactly as `auth.ts` did (do NOT add them to `protocol.ts`; that file is
  append-only for §4 spec constants and these aren't spec values).
- **Strict TS**: no `any`, no non-null `!` across trust boundaries. Handle each `ConnectionState`
  transition explicitly.
- **No `eslint-disable`**; keep the lint warning baseline (70). `no-bitwise` is only allowed under
  ble/crypto/byteLayout — you won't need bitwise here.

## 5. Spec grounding (read these, don't guess)

- **§4.9 connection parameters** — already in `protocol.ts` as `CONNECTION_PARAMS`:
  `supervisionTimeoutMs: 4000` (this is why an involuntary drop is detected ~4s after range loss),
  interval sets for unlocked vs locked-idle, `attMtuDefault: 23`, `phyPrimary: '1M'`. Note
  `LONG_RANGE_PHY_SUPPORTED = false` — **never** re-enable Long Range; range is a safety parameter.
- **§7.1 authority model (CRITICAL, read before coding):** the firmware **dead-man timer** is what
  makes the device safe. The app's connection/reconnect only makes relock *feel fast* — it is NOT
  the authority. **Do not build any logic where the device staying locked depends on this manager
  running.** Reconnect is a UX convenience, not a safety mechanism.
- **Lock state is notification-driven, never optimistic** (CLAUDE.md). This manager owns the *link*,
  not the lock state — don't infer or render lock/unlock from connection state.

## 6. Tests — `src/features/ble/__tests__/connection.test.ts` (new)

Drive everything through `createMockPeripheral(...)` → `MockBleManager` / `MockDevice`. Mirror the
style of `auth.test.ts`. Cover at least:
1. `connect()` happy path → `connecting` → `connected`; `getState` reflects it; state-change
   listener fires in order.
2. `connect()` timeout/failure → returns to `disconnected` as a typed outcome (inject a manager
   whose `connectToDevice` never resolves / rejects).
3. Voluntary `disconnect()` → `disconnected`, and **no reconnect attempt follows** (assert the
   manager does not call `connectToDevice` again).
4. Involuntary drop via `device.simulateAbruptDisconnect()` → `connected → reconnecting →
   connected` when the next connect succeeds (advance the injected scheduler).
5. Backoff exhaustion: reconnect keeps failing → after the bounded max attempts → `disconnected`
   (assert attempt count and that delays grew per the backoff policy).
6. `onStateChange` unsubscribe stops further callbacks; multiple listeners each get events.
7. Background signal suspends reconnect; foreground resumes it.

Determinism: use the injected scheduler seam (not `jest.useFakeTimers` if avoidable, but fake timers
are acceptable if cleaner) so no test waits on real time.
