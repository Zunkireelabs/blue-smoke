## 🔴 STOP HERE FIRST — the age gate may not be a gate

**This is the highest-value open question on the project, and it is not a code problem.**

On 2026-09-10 a test was run that nobody had run before: **one person's government ID submitted
together with a different person's face** (Sadin's ID, Anish's selfie). **Persona returned a
pass, and the app verified the account.**

Two readings, and the code cannot distinguish them:

1. `PERSONA_ENVIRONMENT=sandbox` — sandbox may not run the comparison for real, in which case the
   result says nothing either way; or
2. the template has **no blocking selfie-to-ID face comparison** — absent entirely, or set to
   report-only so a mismatch is recorded without stopping the pass.

This is exactly **OQ-11**, and the three unticked `P2-1.0` boxes in
[`../project-roadmap-todos/TODO-phase-2.md`](../project-roadmap-todos/TODO-phase-2.md) — which
already state that Persona `approved` means *"passed the checks THIS TEMPLATE was configured
with"*, not "is over 18", and not "is the person holding the phone". The difference is that this
is now **measured, not suspected.**

**What our code does correctly, so the gap is not hunted for in the wrong place:**
`persona-webhook` refuses to set `age_verified` unless the inquiry came from exactly the
configured `PERSONA_TEMPLATE_ID` — it logs loudly and leaves the row `pending` otherwise. That
proves *which* template answered. **Nothing in code can prove what that template checks.** Our
half is sound; the vendor-config half is unverified.

### To settle it — Persona dashboard, needs a human with access

On the template `PERSONA_TEMPLATE_ID` actually points to, confirm:

- [ ] **Government ID** and **Selfie** are both required steps
- [ ] **Selfie-to-ID face comparison is blocking**, not report-only ← what the test above implicates
- [ ] **An age requirement (18+) is configured.** An ID that scans cleanly and matches its selfie
      still returns `approved` for a 14-year-old if no `min_age` rule exists
- [ ] The **production** template and environment, since none of the above carries over from sandbox
- [ ] Then **re-run the same experiment against production config** — one person's ID, another
      person's face. It must be refused. If it passes there, the 18+ gate is decorative, and that
      is the entire product promise.

### #33 — "Confirming your verification…" no longer strands users

`useVerificationStatus`'s `refetchInterval` was `data === 'pending' ? 5s : false`. The hook mounts
at sign-in, *before* any inquiry exists, so its first read resolved to `'none'` — not `'pending'`,
so polling never started and never restarted. The webhook's pass was never noticed; only a
force-quit (which remounts the hook) let anyone through.

Now polls until `'verified'`, the only state that cannot change again. That also closed a second
instance nobody had hit: `'declined'` was equally "terminal", and `navigation.tsx` routes declined
users straight back into the flow, so a decline-then-retry would have stranded identically.
`PersonaVerificationScreen` also invalidates the query on create-inquiry success and on the SDK's
`onComplete` — an optimisation that makes the transition immediate rather than up to 5s late, not
the mechanism, and written to fail silently for that reason.
