## 2. 🔴 The one data rule that governs this task

`deviceInfo` bytes 4–15 are **`deviceUid` — the raw MCU unique ID** (§4.3). The spec is explicit,
twice, that the raw UID never leaves the phone: *"the app only ever transmits `SHA-256(UID ‖ salt)`"*
(§3) and *"Raw UID never stored"* (`core_schema.sql`, §5.2.3).

So, in this PR:

- `deviceUid` may exist **in memory**, returned as bytes from the parse function. That is its only
  permitted life.
- **Never** log it, never `console.log` a parsed `DeviceInfo` wholesale, never persist it, never put
  it in an error `detail` string, never send it anywhere.
- **Do not compute `serial_hash`.** That is the OQ-12-blocked work and it is explicitly not in this
  PR. Do not add a salt constant, do not pick a placeholder, do not leave a `TODO` with a guessed
  value in it.

A `detail` string in an outcome may carry **lengths and version numbers only** — the same rule
`auth.ts:320-324` already states for key material.

## 4. What to build

**One new file: `src/features/ble/deviceInfo.ts`.** Follow `auth.ts`'s conventions exactly — module
doc citing the spec subsection, typed outcome, nothing throws across the boundary, every BLE
operation bounded.

### 4.1 The signature — take a connected device, not a `deviceId`

```ts
export async function readDeviceInfo(device: BleDeviceLike): Promise<DeviceInfoOutcome>
```

**This deliberately differs from `authenticate(deviceId, input)`, and the difference is the point.**
§4.3 is a *post-connect* read, and `auth.ts:199-204` already documents the trap: `BleManagerLike`
has no way to fetch a handle for an existing connection, so calling `connectToDevice()` again forces
a disconnect+reconnect on Android. A function that took a `deviceId` would have to do exactly that,
and would drop the connection the caller is holding. Taking the already-connected `BleDeviceLike`
avoids the problem entirely and keeps the connect/discover logic in exactly one place.

Consequence: only the **read** is bounded here. One stage, one budget. Define it as a named local
constant with the same comment `auth.ts:29-38` carries — an app-level operational choice, **not** a
§4 constant, so it does not belong in `protocol.ts`.

### 4.2 The outcome type

```ts
export interface DeviceInfo {
  protocolVersion: number;
  hwRevision: number;
  fwVersion: { major: number; minor: number };
  deviceUid: Uint8Array;              // 🔴 §2 — in memory only, never logged/persisted/sent
  provisioningState: ProvisioningState;
  keyGeneration: number;
}

export type DeviceInfoOutcome =
  | { ok: true; info: DeviceInfo; compatible: boolean }
  | { ok: false; reason: 'timeout' }
  | { ok: false; reason: 'transport'; detail: string };
```

### 4.3 🟠 The compatibility check REPORTS, it does not DECIDE

`compatible` is `info.protocolVersion === PROTOCOL_VERSION`. That is the whole check.

**Do not add policy.** Do not refuse to return the info on a mismatch, do not throw, do not disconnect,
do not route anywhere. The reason is not style: **the spec never says what the app should do when
`protocolVersion` disagrees.** §4.3 states the device reports `0x01`, and the header says changing §4
requires a bump plus written notice — but no section defines the client's behaviour on mismatch. That
is a real gap, and per CLAUDE.md an unspecified value or behaviour gets **flagged, not invented**.

The honest shape is therefore: this module reports the fact, and the first real caller (the pairing
screen, Part 2b) makes the decision once someone has ruled on it. Returning `ok: true` alongside
`compatible: false` is intentional — the read *succeeded*; it is the device that is a different
version, which is a product decision, not a transport failure.

**Report this gap in your §7 findings** so it goes to the firmware walkthrough (OQ-6). Do not resolve
it yourself.

### 4.4 Failure paths, all typed

- Read times out → `{ ok: false, reason: 'timeout' }`.
- `characteristic.value` is `null` → `{ ok: false, reason: 'transport', detail: ... }`.
- Byte length ≠ `CHARACTERISTIC_LENGTH_BYTES.deviceInfo` → `{ ok: false, reason: 'transport', detail }`
  citing expected vs actual **lengths only**.
- `provisioningState` outside 0/1/2 → this is a malformed device, not a valid state.
  `{ ok: false, reason: 'transport', detail }` naming the offending value. Do **not** silently coerce
  it, and do **not** widen the `ProvisioningState` type to accept it.
- Anything else thrown by the read → the same single-catch → `transport` shape `auth.ts:316-326` uses.

Base64: `auth.ts` has hand-rolled `base64ToBytes` and explains why (`auth.ts:97-103` — Hermes
polyfills neither `atob` nor `btoa`). **Do not duplicate it** and **do not import it from `auth.ts`**
(it is not exported, and exporting it would mean editing `auth.ts`, which §1 forbids). Instead, note
in your report that base64 conversion is now needed by a second module and should be extracted to a
shared helper in a follow-up — and for *this* PR, write the minimal decoder you need locally with a
comment pointing at the duplication. **Flagging the duplication is required; resolving it is not in
scope.**

## 5. Tests — `src/features/ble/__tests__/deviceInfo.test.ts`

Against `createMockPeripheral()` from `tools/mock-peripheral/bleAdapter`, the same way
`auth.test.ts` does it. The mock already serves §4.3 (`deviceCore.ts:340`, `:390-399`) and takes a
`provisioningState` config option (`:116-117`), defaulting to `PROVISIONED`.

Required cases:

1. A real mock read parses every field correctly — assert **each field individually**, including
   `deviceUid` byte-for-byte.
2. `compatible: true` against the mock (which speaks `0x01`).
3. `compatible: false` for a device reporting a different `protocolVersion` — and `ok` is still
   `true`, with `info` fully populated.
4. Each of the three `provisioningState` values round-trips, driven through the mock's config option.
5. An out-of-range `provisioningState` → typed `transport` outcome.
6. `value: null` → typed `transport` outcome.
7. Wrong byte length → typed `transport` outcome, detail naming both lengths.
8. A hung read → `{ ok: false, reason: 'timeout' }`, fake timers, resolving well inside the test
   timeout.
9. **Nothing throws.** Every failing case asserted with `.resolves`, never a `try/catch`.

### 🔴 Fixture rule — this is the trap that has been hit twice on this branch

**Every fixture must have distinct bytes.** A `deviceUid` of `new Uint8Array(12)` or `fill(0xAA)`
**cannot detect a wrong offset or a wrong length** — `readBytes(buf, 4, 12)` and `readBytes(buf, 5, 12)`
return the same thing, and the test passes while the parser is wrong. Use `0x40 + i` or similar.
This exact defect shipped twice: `SESSION_ID = fill(0x22)` hid every positional CMAC error
(`3d15000`), and the design-system `contrastPairs` gap before it.

Pick field values that are **mutually distinguishable too** — if `hwRevision` and `keyGeneration`
are both `0x07`, swapping their offsets is undetectable. Give every scalar field a different value.

### The mutations your tests must kill — paste both runs for each

| # | Mutation | Must fail |
|---|---|---|
| 1 | `deviceUid` offset `+1` in the parser | the field-by-field test |
| 2 | `deviceUid` length `12` → `11` | the field-by-field test |
| 3 | swap the `hwRevision` and `keyGeneration` offsets | the field-by-field test |
| 4 | `fwVersion` major/minor read order swapped | the field-by-field test |
| 5 | `compatible` hardcoded to `true` | the mismatch test |
| 6 | the read's `withTimeout` made a passthrough | the hung-read test |
| 7 | the length check deleted | the wrong-length test |
| 8 | the `provisioningState` range check deleted | the out-of-range test |

**A mutation that survives is a finding, not a footnote** — report it plainly, including any you
cannot kill and why. That has happened legitimately before (`6bad269`, finding 7) and the honest
report was the right answer.
