## 2. ⚠️ Be honest about what lint can and cannot enforce

This is the most important section. `CLAUDE.md`'s actual rule is *"never log an `inquiry_id`
**alongside anything that could re-identify** the person"* — a **data-flow property**. ESLint
does not do data-flow. It cannot see that:

```ts
const payload = { id: inquiryId, who: user.email };
logger.info(payload);            // ← the rule is violated; no lint rule will catch this
```

So build a **tripwire, not a proof**, and say so in the config comment. A guard that implies it
proves the rule is worse than no guard, because it invites people to stop thinking. The realistic
mistake this catches is the one that actually happens: someone debugging adds
`console.log(inquiryId)` and it survives review.

**Do not** attempt a clever data-flow rule, and **do not** describe the result as "enforced" in
any comment or doc. "Catches the direct case" is the honest phrasing.

- `no-restricted-imports` — restore the **analytics / crash-reporting / persistence** portion of

  than retyping it from memory. Keep `@sentry/*`, `*analytics*`, `*crashlytics*`, the Firebase

    producing a report containing the ID" — that reasoning is obsolete under Persona (we never
    hold the ID). The live reason is the `inquiry_id` pairing rule plus the standing "no
    analytics in this subtree, ever" line. Write the current reason.
  - **Keep `react-native-keychain` restricted?** Decide and justify in your report. My read: yes
    — nothing in this subtree should be persisting anything — but it is a judgement call and I
    want your reasoning, not silent compliance.

### 3.2 Edge Functions holding an `inquiry_id` — `supabase/functions/persona-webhook/**`, `supabase/functions/create-inquiry/**`

🔴 **`no-console` must NOT be applied here.** Both functions use `console.error` for operational
logging that is genuinely needed — 9 call sites, all deliberate, none logging an identifier. A
blanket ban would either break the build or push someone into deleting useful diagnostics.

Instead add a **targeted** `no-restricted-syntax` rule flagging an `inquiry_id`-ish identifier
appearing inside a `console.*` call. This selector is verified working on this exact ESLint
version:

```js
{
  selector: "CallExpression[callee.object.name='console'] Identifier[name=/inquiry_?[iI]d/]",
  message: "…",
}
```

Also apply the analytics/crash `no-restricted-imports` patterns here — the "no analytics in the
verification path, ever" rule is about the data, not about which directory it lives in, and these
two functions are squarely in that path.

## 4. 🔴 The guard must prove it bites — this is the deliverable

Every green tick on this project today has been checked by breaking the thing it tests. Five
false-green tests were found this way, one of them in this very repo's lint guard story. So:

**Add `tools/lint-guard/__tests__/verificationGuard.test.ts`** (a jest test in the `app` project,
or a fourth project if that is cleaner — your call, justify it) that:

1. Writes a **temporary probe file** into `src/features/verification/` containing a violation
   (e.g. `console.log('inquiry', inquiryId)` plus a restricted import).
2. Shells out to `npx eslint <probe> --format json` and parses the result.
3. Asserts the expected rule IDs actually fired.
4. **Deletes the probe in a `finally` block**, so a failing assertion cannot leave a file behind
   that breaks `npm run lint` for everyone.

**The trap:** a probe committed inside `src/features/verification/` would make `npm run lint`
fail for the whole repo. It must be created and removed by the test, never committed. Add the
probe filename to `.gitignore` as a second line of defence, and say in the test's header why.

Assert on **rule IDs**, not on message text — messages get reworded.

Cover, at minimum:
- `console.log` of an `inquiryId` in the RN subtree → `no-console` fires
- a `@sentry/react-native` import in the RN subtree → `no-restricted-imports` fires
- `console.error(\`… ${inquiryId}\`)` in `persona-webhook/` → `no-restricted-syntax` fires
- a **clean** file in the same directory → **no** errors (proves the rule is not just always-on,
  which is the lint equivalent of a vacuous test)

That last case is not optional. A rule that fires on everything is indistinguishable from a
working rule until it blocks someone's legitimate commit.
