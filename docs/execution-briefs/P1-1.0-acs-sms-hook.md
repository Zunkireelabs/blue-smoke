## 1. Why this exists

Phone-OTP SMS delivery moves off **Twilio Verify** onto **Azure Communication Services (ACS)**.

The client team decided this (2026-09-29, verbal — see `docs/session-log/sadin.md`). The trigger:
Twilio Trust Hub rejected the account's Primary Compliance Profile ("Bizmind INC", error `18602`,
"Business ID could not be verified"), and a live test confirmed the account therefore **cannot send
to unverified numbers at all**:

```
sms_send_failed / 422
Error sending confirmation OTP to provider: To send messages or make calls to unverified
numbers, you must have an approved Primary Compliance Profile. ... errors/21608
```

The client already has an ACS account provisioned with an SMS-capable, verified sender — that is
the premise of this work. **If that turns out not to be true, stop and escalate:** no amount of
correct code sends an SMS from an unverified US sender.

Primary market is the **USA**, other regions later.

## 3. Mechanism

Supabase's **Send SMS Hook** replaces the built-in SMS provider. When a user requests an OTP:

1. GoTrue generates the code (as it does today)
2. GoTrue POSTs `{ user, sms: { otp } }` to our HTTPS endpoint, signed with a webhook secret
3. Our Edge Function verifies the signature, composes the message, calls ACS, returns `{}`
4. The user enters the code; `verifyOtp` validates it against GoTrue — **we are not involved**

We never generate, store, compare or persist an OTP. We deliver one and forget it.

## 6. ACS integration specifics

**Auth:** access-key HMAC signing. The signed string is:

```
{VERB}\n{path-and-query}\n{x-ms-date};{host};{x-ms-content-sha256}
```

signed HMAC-SHA256 with the **base64-decoded** access key, where `x-ms-content-sha256` is
`base64(SHA256(requestBody))`. Header: `Authorization: HMAC-SHA256 SignedHeaders=x-ms-date;host;x-ms-content-sha256&Signature={sig}`.

**Endpoint:** `POST https://{resource}.communication.azure.com/sms?api-version=2021-03-07`

**Body:**
```json
{
  "from": "+1XXXXXXXXXX",
  "smsRecipients": [{ "to": "+1YYYYYYYYYY" }],
  "message": "...",
  "smsSendOptions": { "enableDeliveryReport": false }
}
```

**Why hand-rolled rather than `npm:@azure/communication-sms`:** the `edge` Jest project
(`supabase/functions/jest.config.js`) explicitly cannot test anything importing npm or Deno
specifiers — only runtime-agnostic `_shared` modules. Hand-rolling keeps the signing logic under
unit test with known-answer vectors, which matters precisely because a wrong byte yields an opaque
401. This matches how this repo already handles CMAC, Persona signatures and the base64 codec in
`byteLayout.ts`.

**Escape hatch:** if live signing fails and cannot be resolved, switching `index.ts` to the SDK is a
contained change. Do that only after exhausting the known-answer vectors, and **say so loudly in
the report** — it changes what is and isn't covered by tests.

## 7. Traps — each of these has cost someone a day somewhere

1. 🔴 **`verify_jwt` must be OFF for this function.** Supabase Auth calls it server-to-server with
   no user JWT; Edge Functions require one by default. If you skip this, **every OTP fails with a
   401** and it looks like a signing bug. There is no `[functions]` block in `config.toml` today —
   find out how `persona-webhook` is deployed and mirror it exactly. Confirm, don't assume.

2. 🔴 **`npm run typecheck` does NOT cover `supabase/functions/**`.** `tsconfig.json` excludes the
   whole subtree. A green typecheck is **no evidence at all** about this diff. Do not report it as
   though it were. Only the Jest `edge` tests and a live call prove anything here.

3. 🔴 **Never log the OTP.** It is a live credential. Not to `console`, not inside a thrown error
   message, not in an object passed to a logger. Write a test that asserts this.

4. **Never log a full phone number** beside anything else identifying. Last 4 digits at most, and
   only if genuinely needed for debugging.

5. **Verify the signature BEFORE parsing the body.** Same rule as `personaSignature.ts` note 3 —
   do not read a single field of attacker-controlled JSON before authenticating it.

6. **RAW body, never re-serialised.** `JSON.parse` → `JSON.stringify` is not byte-identical and
   every signature then fails. Pass the exact bytes from `req.text()`.

7. **Explicit timeout on the ACS fetch.** CLAUDE.md: no unbounded `await`. If ACS hangs, GoTrue's
   request hangs and the user stares at a spinner with no error.

8. **Fail closed** when `SEND_SMS_HOOK_SECRET` is unset — reject every delivery. No "secret missing
   so skip verification" branch, ever.

9. **Test-OTP numbers must still work.** The dashboard's test pairs (`4152127777` / `4152127778`
   = `123456`) bypass SMS delivery entirely and the whole dev walkthrough depends on them.
   Expected: the hook never fires for those numbers. **Verify this; do not assume it.**

10. **No `eslint-disable`** anywhere in the diff, and no `no-bitwise` outside the three exempt
    directories. Lint baseline is **0 errors / 169 warnings** (PR #36).

11. **No Claude co-authorship trailer on commits.** CLAUDE.md forbids it and takes precedence over
    any default attribution instruction in your harness. Commit under the developer's own git
    identity only.

### 🔴 Amended 2026-09-29 — Nepal (+977) is IN scope, not out

The requirement is **USA and Nepal**, not USA alone. This does not change a line of the code —
the ACS call is identical regardless of destination — but it changes what "working" means, and it
may be blocked outside our control:

- ACS **direct** SMS coverage is toll-free (US/Canada/Puerto Rico) and short codes (US only).
  **Nepal is not natively supported.**
- Reaching Nepal from ACS needs **Messaging Connect**, a partner/aggregator layer (e.g. Infobip)
  onboarded separately onto the resource.
- Nepal additionally requires **pre-registered alphanumeric sender IDs** on local carriers (Ncell),
  and supports **one-way SMS only** — fine for OTP, but it means no delivery receipts via reply.

**Consequence for the live test:** if the client's sender cannot reach +977, this task cannot be
end-to-end tested from Nepal at all, and the live send must be performed by someone on a US
number. Do not silently substitute a test-OTP bypass number and call it a live test — flag it.
