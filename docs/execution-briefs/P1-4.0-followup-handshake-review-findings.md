## 2. Finding 1 🔴 — the handshake tests cannot detect a wrong CMAC input

### What is wrong

`src/features/ble/__tests__/auth.test.ts:22-23`:

```ts
const K_DEV = new Uint8Array(16).fill(0x11);
const SESSION_ID = new Uint8Array(16).fill(0x22);
```

Every byte is identical, so `sessionId[0..4]` and `sessionId[1..5]` are **the same four bytes**. The
proof input is therefore invariant under any off-by-one, wrong-slice, or wrong-length error in that
field — which is precisely the field spec §4.5 flags as easy to misread, and which `auth.ts:135-137`
carries a dedicated comment about.

### The proof

Changing `auth.ts`'s `readBytes(sessionId, 0, 4)` to `readBytes(sessionId, 1, 4)`:

| Fixture | Result |
|---|---|
| `fill(0x22)` (as committed) | **6 passed, 0 failed** — mutation invisible |
| `0x20 + i` (distinct bytes) | **2 failed** — mutation caught |

This is the same failure shape as the contrast-pair defect found on 2026-08-07: passing by
coincidence of value rather than by correctness.

It matters more than a normal test gap because a wrong `K_sess`-derived proof and a *forged* proof
are indistinguishable by design — a mistake here produces no diagnostic and surfaces only against
real firmware on Day 26.

### The fix

```ts
const K_DEV = Uint8Array.from({ length: 16 }, (_, i) => 0x10 + i);
const SESSION_ID = Uint8Array.from({ length: 16 }, (_, i) => 0x20 + i);
```

Verified: with these fixtures and no mutation, all 6 tests still pass; with the mutation, 2 fail.

Then **audit every other fixture in the file for the same weakness** — `wrongKSess` is
`fill(0x99)`, and any all-zero `Uint8Array(16)` used as a payload has the identical problem. A
fixture whose bytes are all equal cannot detect a positional error. Prefer distinct-byte patterns
everywhere, including in `crypto.test.ts` if any fixture there shares the trait.

## 3. Finding 2 🔴 — four unbounded `await`s; CLAUDE.md requires every BLE op to be bounded

### What is wrong

CLAUDE.md, Code conventions: **"Every BLE operation has an explicit timeout. No unbounded `await`."**

`auth.ts` bounds exactly one thing — the `commandResult` notification — and does not even start that
timer until every preceding operation has resolved (`auth.ts:240`). These are all unbounded:

```
auth.ts:155  await manager.connectToDevice(deviceId)
auth.ts:156  await device.discoverAllServicesAndCharacteristics()
auth.ts:206  await device.readCharacteristicForService(...)      // authChallenge
auth.ts:223  await device.writeCharacteristicWithResponseForService(...)   // frame 1
auth.ts:231  await device.writeCharacteristicWithResponseForService(...)   // frame 2
```

### The proof

A manager/device double whose operation never settles, raced against a 15s deadline:

```
op=connect  → HUNG        op=discover → HUNG
op=read     → HUNG        op=write    → HUNG
```

`authenticate()` never settles. The caller has no recovery and the UI spinner never stops. A BLE
read that never calls back is an ordinary event — a device leaving range mid-operation, or
CoreBluetooth simply not invoking the callback — which is exactly why the rule exists.

The existing timeout test passes because it exercises only the notification path. It is a true test
of a narrow property, being read as a guarantee about the whole function.

> **In fairness: the previous brief under-specified this.** Its §10 item 5 said "an unbounded await
> on the `commandResult` notification," which the implementation satisfied. CLAUDE.md's rule is
> broader and governs. This is a brief defect, not an execution defect — but it still has to be fixed.

### The fix

Add a small local helper and wrap **every** BLE call:

```ts
async function withTimeout<T>(operation: Promise<T>, ms: number, stage: HandshakeStage): Promise<T>
```

Give each stage its own budget rather than one number for everything — connecting legitimately takes
longer than a characteristic read. Define them as named local constants with a comment saying they
are app-level operational choices, **not** §4 constants (so they do not belong in `protocol.ts` —
same reasoning as the existing `HANDSHAKE_RESPONSE_TIMEOUT_MS`).

A timeout must produce a typed outcome, never a throw (§4 below). Extend the existing variant with
the stage so a field report can distinguish "never connected" from "connected but silent":

```ts
| { ok: false; reason: 'timeout'; stage: 'connect' | 'discover' | 'read' | 'write' | 'result' }
```

**Test it:** one case per stage, driven by a double whose operation never resolves, asserting
`authenticate()` resolves to the right `stage` well inside the test timeout. Use fake timers so the
suite stays fast. These five tests are the deliverable — the fix without them re-opens the same hole
the moment someone refactors.

## 4. Finding 3 🔴 — `authenticate()` throws, contradicting its own contract

### What is wrong

`auth.ts:5-8` states: *"Everything a BLE-failure path can do resolves to a typed `HandshakeOutcome`
— nothing across this boundary throws, same convention as `AuthClient`'s `AuthResult`."*

It does throw, on at least three paths:

- `auth.ts:155` — `manager.connectToDevice()` sits **outside** the `try` (which opens at line 204),
  so any rejection escapes. Confirmed: `authenticate()` with an unknown `deviceId` **throws** rather
  than resolving. (`MockBleManager.assertKnownDevice` throws; real `BleManager` rejects on a
  connection failure, which is the ordinary case, not an exotic one.)
- `auth.ts:211` — `throw new Error('authChallenge read returned no value')`.
- `auth.ts:215` — `throw new Error('authChallenge: expected N bytes, got M')`.

The previous report disclosed the second and third under its deviation 2, so this is a known-and-
stated gap rather than a hidden one — but it leaves callers needing both a `try/catch` **and** an
outcome switch, which is exactly the ambiguity the typed-outcome convention exists to remove. The
pairing screen in Part 2 is the first caller, and it will get this wrong.

### The fix

Bring **every** path inside the contract. Widen `HandshakeOutcome` with a variant for
protocol/transport failures that are neither an auth decision nor a timeout — e.g.

```ts
| { ok: false; reason: 'transport'; stage: HandshakeStage; detail: string }
```

`detail` is for logs and must stay free of key material — **never** interpolate `kSess`, the proof,
or the nonce into it.

Move the `connectToDevice` call inside the `try`, or wrap the whole body. Note the ordering
constraint: `subscription.remove()` in the existing `finally` is only valid once the subscription
exists, so structure the error handling so a connect failure does not try to remove a subscription
that was never created.

**Test it:** `authenticate()` against a manager that rejects on connect resolves to a typed outcome
and does not throw. Add the malformed-`authChallenge` case too (a device double returning `null`,
and one returning the wrong byte length).

## 5. Finding 4 — `auth.test.ts` is excluded from `typecheck`, and there is a better fix

`tsconfig.json` adds `src/features/ble/__tests__/auth.test.ts` to `exclude`. The diagnosis in that
comment is **correct and was verified** — `exclude` does not stop transitively-imported files being
checked, so importing the mock does pull `Buffer`-typed files into a program whose `types: ["jest"]`
deliberately omits `@types/node`.

But the file is now permanently unchecked, and the previous report correctly predicts P3-2.0 and
P3-3.0 hitting the same wall and growing the list.

**Verified alternative:** `auth.test.ts` type-checks **clean (exit 0)** under a config identical to
root but with `types: ["node", "jest"]`. So add a second TS project for test files needing Node
ambients — e.g. `tsconfig.test.json` extending root with that one override and including the
affected tests — and have `npm run typecheck` run it alongside the existing two. App code keeps its
`Buffer`-free program; the test regains coverage; P3-2.0/P3-3.0 get a home rather than another
`exclude` entry.

Remove the `exclude` entry as part of this. Keep the explanatory comment, moved to the new config.

## 6. Finding 5 — result codes other than `OK` / `AUTH_FAILED` / `RATE_LIMITED` are silently dropped

`auth.ts:189-200` handles three codes. Anything else — `FAULT` (0x08), `NOT_ACTIVATED` (0x04),
`BUSY` (0x07), `INVALID_PARAM` (0x06) — falls out of the callback with no action and surfaces
`HANDSHAKE_RESPONSE_TIMEOUT_MS` later as a timeout.

CLAUDE.md: **"Handle every result code distinctly (spec §4.7). No generic catch-all for the 10
command results."** A `FAULT` reported to the user and the logs as a timeout is a misdiagnosis, and
the §4.7 codes exist precisely so failures are attributable.

**Fix:** resolve a distinct typed outcome carrying the received `resultCode` for any code that is
not `OK`. Keep `AUTH_FAILED`/`RATE_LIMITED` as they are — callers branch on them — and let the rest
arrive as an explicit "unexpected result code" outcome rather than silence. Add one test driving an
unexpected code through the mock (`core.forceNextCommandResult(...)`) and asserting it does **not**
present as a timeout.

Note the existing `commandId !== HANDSHAKE_RESULT_COMMAND_ID` guard is correct and should stay —
ignoring another command's result is right; ignoring *this* handshake's result is not.
