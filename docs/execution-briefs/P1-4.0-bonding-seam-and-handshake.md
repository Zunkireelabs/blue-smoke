## 5. `crypto.ts` — AES-128-CMAC, independently written

### 5.1 Why independent, and what that does and does not mean

`tools/mock-peripheral/crypto.ts`'s own header explains this: if the app and the mock shared
one CMAC implementation, a bug in it would cancel out in every test that runs the two against
each other, and only surface against real hardware. Read that file for the algorithm (RFC 4493
§2.3/§2.4 — subkey generation, left-shift-and-XOR-Rb, padding) but **write your own
implementation from it**, don't import or transcribe it. The RFC 4493 Appendix A test vectors
below are public and fine to reuse verbatim — reusing published test vectors isn't the kind of
sharing that defeats the independence argument, reusing the *implementation* is.

### 5.2 No `node:crypto` — this runs on Hermes

The mock's `crypto.ts` uses `node:crypto` (`createCipheriv('aes-128-ecb', ...)`), which does not
exist in the React Native runtime. Add **`@noble/ciphers`** (zero-dependency, audited, pure JS,
no native module — works unchanged under Hermes and under Jest) to get a raw AES-128 block
encrypt primitive, then build CMAC's subkey generation and MAC computation on top of it
yourself, same structure as the mock's `crypto.ts` (`generateSubkeys`, `xorBytes`,
`leftShiftOneBit`, `padBlock`, the RFC 4493 §2.3 constant `Rb = 0x00...0087`).

⚠️ **The exact `@noble/ciphers` call signature for a raw, unpadded single-block ECB encrypt is
not pinned down here — verify it against `node_modules/@noble/ciphers`'s own `.d.ts`/README for
the version npm installs, don't guess.** Whatever the call turns out to be, prove it's the
*raw block cipher* (no padding, exactly 16 bytes in, exactly 16 bytes out) with this FIPS-197
Appendix B vector before building anything on top of it — if this doesn't pass, nothing above it
can be trusted regardless of what the CMAC vectors below say:

```
key:        000102030405060708090a0b0c0d0e0f
plaintext:  00112233445566778899aabbccddeeff
ciphertext: 69c4e0d86a7b0430d8cdb78070b4c55a
```

### 5.3 The RFC 4493 Appendix A vectors — reuse these exactly, add the constant to `protocol.ts`

```
KEY = 2b7e151628aed2a6abf7158809cf4f3c
M   = 6bc1bee22e409f96e93d7e117393172a
      ae2d8a571e03ac9c9eb76fac45af8e51
      30c81c46a35ce411e5fbc1191a0a52ef
      f69f2445df4f9b17ad2b417be66c3710

Mlen=0  → AES-CMAC = bb1d6929e95937287fa37d129b756746
Mlen=16 → AES-CMAC = 070a16b46b4d4144f79bdd9dd04a287c   (M[0:16])
Mlen=40 → AES-CMAC = dfa66747de9ae63030ca32611497c827   (M[0:40])
Mlen=64 → AES-CMAC = 51f0bebf7e3b9d92fc49741779363cfe   (M[0:64])
```

(Copied from `tools/mock-peripheral/__tests__/cmac.rfc4493.test.ts` — same public RFC vectors,
your implementation independent, per §5.1.)

Export `aesCmac(key: Uint8Array, message: Uint8Array): Uint8Array` — nothing else needs to be
public. No HKDF here: unlike the device and the server, the app never derives `K_sess` — it
receives it ready-made from `issue-device-session` (spec §5.4 step 10, out of scope this PR
anyway per §7).

Also add, to `protocol.ts`'s §4.5 section (append only, do not touch any existing line):

// §4.5 — sentinel commandId a handshake result is written under (tools/mock-peripheral's
// deviceCore.ts HANDSHAKE_COMMAND_ID_SENTINEL). Unused by any real command (§4.6); §4.5's prose

## 6. `auth.ts` — the §4.5 handshake

### 6.1 Byte layout helper

`tools/mock-peripheral/byteLayout.ts` cannot be imported (it's `tools/`, never a runtime
dependency — see that package's README, first paragraph). Write a small
`src/features/ble/byteLayout.ts` with just what you need: `writeUint8`, `writeBytes`,
`writeUint24LE`, `readUint8`, `readBytes`. Trivial LE encode/decode — the "write it
independently" argument in §5.1 is about crypto specifically, not this.

### 6.2 The interface — replace the stub, don't preserve its exact shape

The current stub in `src/features/ble/auth.ts`:

```ts
export interface AuthSession {
  sessionId: string;
  keyGeneration: number;
  expiresAt: number;
}
export interface AuthHandshake {
  authenticate(deviceId: string, kSess: Uint8Array): Promise<AuthSession>;
}
export function createAuthHandshake(): AuthHandshake {
  throw new Error('P1-4.0');
}
```

`authenticate(deviceId, kSess)` alone is under-specified — the handshake also needs
`session_id`, `keyGeneration`, and `expiresAtDelta`, all of which come from
`issue-device-session`'s response (§5.4 step 10) and none of which this app code should invent.
This is `auth.ts`, not `protocol.ts` — it's yours to change freely, it has no other callers yet.
Change the shape to take a manager and the full server-issued bundle:

```ts
export interface AuthResponseInput {
  sessionId: Uint8Array; // 16B, from issue-device-session
  kSess: Uint8Array; // 16B, from issue-device-session
  keyGeneration: number; // 0-255
  expiresAtDelta: number; // seconds, ≤ SESSION_EXPIRY_MAX_DAYS worth
}

export type HandshakeOutcome =
  | { ok: true; session: AuthSession }
  | { ok: false; resultCode: typeof ResultCode.AUTH_FAILED | typeof ResultCode.RATE_LIMITED }
  | { ok: false; reason: 'timeout' };

export interface AuthHandshake {
  authenticate(deviceId: string, input: AuthResponseInput): Promise<HandshakeOutcome>;
}

export function createAuthHandshake(manager: BleManagerLike): AuthHandshake { /* ... */ }
```

(Adjust names if you prefer — keep the properties and the fact that failure is a typed
outcome, not a thrown error. Every BLE failure path in this codebase resolves, it doesn't
throw across this boundary — same convention as `AuthClient`'s `AuthResult`.)

### 6.3 The steps, per §4.5 — do not reorder, do not invent a value not listed here

1. Connect (`manager.connectToDevice(deviceId)` if not already connected) and
   `discoverAllServicesAndCharacteristics()`.
2. **Subscribe to `commandResult` (C6) before writing anything** —
   `monitorCharacteristicForService(BLE_SERVICE_UUID, BLE_CHARACTERISTIC_UUIDS.commandResult, listener)`.
   Subscribe-before-write, not read-after-write: the device notifies once, asynchronously, and a
   read issued after the write could race a notification that already fired. Wrap the wait in
   an explicit timeout (CLAUDE.md: no unbounded `await` on a BLE operation) — **there is no
   spec-defined value for this timeout; it's an app-level operational choice, not a §4
   constant, so it does not belong in `protocol.ts`.** Use a local constant in `auth.ts`,
   commented as such, e.g. `const HANDSHAKE_RESPONSE_TIMEOUT_MS = 5000;` — well inside
   `AUTH_NONCE_TTL_MS` (30s) so a timeout here still leaves room to retry against the same
   nonce. Flag in your report if you pick a different value and why.
3. Read `authChallenge` (C2) → `N`, 16 bytes (`AUTH_NONCE_LENGTH_BYTES`).
4. Compute `proof = aesCmac(kSess, concat(AUTH_PROOF_FIXED_PREFIX, PROTOCOL_VERSION, N, sessionId[0..4], expiresAtDeltaLE3))`.
   Note: `session_id[0..3]` in the spec prose means **the first 4 bytes**, half-open range —
   confirm this against `deviceCore.ts`'s `evaluateHandshake` (`frame1.sessionId.subarray(0, 4)`)
   rather than the English alone.
5. Write frame 1 to `authResponse` (C3):
   `[AuthResponseFrameIndex.FRAME_1, sessionId (16B), keyGeneration (1B), 0x00, 0x00]` — 20 bytes,
   per `AUTH_RESPONSE_FRAME_1_LAYOUT`.
6. Write frame 2 to `authResponse` (C3):
   `[AuthResponseFrameIndex.FRAME_2, proof (16B), expiresAtDelta as uint24 LE (3B)]` — 20 bytes,
   per `AUTH_RESPONSE_FRAME_2_LAYOUT`. **Two separate
   `writeCharacteristicWithResponseForService` calls, frame 1 fully awaited before frame 2 is
   sent** — the mock's `writeAuthResponseFrame` is called once per write, not once per
   `authenticate()`, so sending both frames concatenated in one write is wrong and won't match
   the wire format hardware expects either.
7. Await the `commandResult` notification (from step 2) or the timeout.
8. Decode: `commandId` must equal `HANDSHAKE_RESULT_COMMAND_ID` (0x00, §5.3) — if it's anything
   else, something unrelated wrote to this characteristic (e.g. an in-flight lockCommand result)
   and the notification should be ignored, not treated as this handshake's answer, until either
   the real one arrives or the timeout fires. Then branch on `resultCode`:
   `ResultCode.OK` → success, return `{ ok: true, session: { sessionId, keyGeneration, expiresAt: now + expiresAtDelta*1000 } }`.
   `ResultCode.AUTH_FAILED` / `ResultCode.RATE_LIMITED` → the corresponding typed failure.
9. Unsubscribe (`remove()`) in a `finally`, whichever branch was taken.

## 7. Non-scope — the rest of `P1-4.0`, and why it's a separate PR

deliberately **not** in this PR:

- **`serial_hash` computation and the `issue-device-session` call.** `docs/TECHNICAL_SPEC.md`
  line 613 / the `core_schema.sql` migration both define `serial_hash` as
  `SHA-256(deviceUid ‖ server_salt)` — but the salt value is **never specified anywhere** in the
  spec, the migration, or `issue-device-session/index.ts` (which receives `serial_hash`
  pre-computed from the client and never derives it itself). Flow B (§2.3) says the *app*
  computes `serial_hash`, which means the app needs the salt — but "server_salt" as a name
  suggests it might not be something the app should know. **This is a genuine spec gap, not
  something to guess at** — CLAUDE.md is explicit that an unspecified value gets flagged, not
  invented. Raise it with Sadin before the next brief in this area is written; don't silently
  pick a value (e.g. an empty salt, or a hardcoded string) to make progress, since a client-
  guessed salt that doesn't match whatever the device/manufacturing process actually uses would
  fail `serial_hash` lookups silently (every device would appear "unseen" forever, landing on
  the `upsert` path instead of matching the real row).
- `deviceInfo` read + `protocolVersion` compatibility check.

- `K_sess` Keychain/Keystore storage (needs a real `K_sess` flowing through the app first —

- Any actual pairing/bonding **screen** — no UI in this PR, only the seam and the crypto/protocol

- LE Secure Connections OS-level bonding UX, bond-lost recovery, and the "bonded-but-
