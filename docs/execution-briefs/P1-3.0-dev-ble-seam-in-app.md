# Execution Brief — run the app against the mock peripheral, in the app

**Task ID:** `P1-3.0` (enabling work for `DV-*` / `LK-*`) · **Phase:** 1
**Branch:** `feature/P1-3.0-dev-ble-seam-in-app` — branch off `stage`, push on day one.
**Size:** medium. The value is high: `DV` and `LK` are **0 of 14 screens built**, and this is what
makes them buildable and reviewable before hardware arrives (~Day 26).

---

## 1. Why this exists

The app cannot show a single device screen on a simulator. Tapping **Pair a device** spins forever
(the `P1-2.0` gate defect), and even with that fixed you would land on `DeviceScan` with no device
to find, because an iOS simulator has no Bluetooth radio.

Meanwhile `tools/mock-peripheral` is a §4-faithful simulation of the firmware — three layers, RFC
4493 vectors verified against published values, ~51 tests — and `BleClientProvider` already takes an
injectable `manager?: BleManagerLike` for exactly this purpose. `MockBleManager`
(`tools/mock-peripheral/bleAdapter.ts:176`) already implements that interface.

**The two halves have simply never been connected**, and there is one concrete reason why.

---

## 2. The actual blocker — read this before designing anything

`providers.tsx` says the mock is *"deliberately never imported from this file or anywhere under
`src/`"* because it is pure-Node. Specifically:

- `deviceCore.ts:100` — `import { randomBytes } from 'node:crypto'`
- `crypto.ts:13` — `import { createCipheriv, hkdfSync, timingSafeEqual } from 'node:crypto'`

🔴 **A top-level `node:crypto` import breaks the Metro bundle even if the code never runs.** Metro
resolves imports statically; guarding the *call site* with `__DEV__` does nothing. The import itself
has to stop existing on any path reachable from `src/`. If you take one thing from this brief, take
that — it is the trap that makes the obvious approach fail late, at `bundle:check`, rather than
early.

### 2.1 Approach: invert the dependency — do **not** write a second mock

The tempting shortcut is a fresh, crypto-free fake under `src/`. **Don't.** The whole value of
`tools/mock-peripheral` is that it implements the §4 contract faithfully and is cross-verified; a
second, looser fake means building `DV`/`LK` UI against a fiction, and the entire point of this
exercise is that what we build against is what the firmware will actually do. Two mocks also drift,
and the looser one always wins because it is easier.

Instead: **`deviceCore` should declare the crypto and RNG it needs and receive them from its
caller.** The RNG is already half-way there — `deviceCore.ts:123` documents it as injectable
("inject for deterministic tests"). Finish that job for both dependencies, so:

- the **Node test harness** supplies the existing `node:crypto` implementations (nothing about the
  current test suite's behaviour changes), and
- the **app** supplies its own, or a stub for flows that do not need crypto at all.

`crypto.ts` then stops being imported by `deviceCore`/`bleAdapter` and becomes what it always
should have been: the Node-side implementation of an interface, not a hard dependency of the
simulation.

**Verify the claim, don't trust this brief:** confirm that scan → connect → discover needs no CMAC
or HKDF at all. If some path does, say so and scope it rather than stubbing something security
-shaped into silence.

## 3. What to build

### 3.1 A selectable radio state

`MockBleManager.state()` returns `'PoweredOn'` unconditionally (`bleAdapter.ts:183`). That is right
for tests and wrong for this task: it makes every gate screen unreachable in the app.

Make the state **selectable** so a developer can drive `PoweredOn`, `PoweredOff`, `Unauthorized`,
`Unsupported` and `Unknown` on demand. This is the single highest-value part of the task — those
five states map to ON-7/8/9/10 and the gate spinner, and today the only one anyone can observe is
whichever one the hardware happens to be in.

> This is also what makes the **`P1-2.0` Bluetooth-gate fix** properly testable. That brief's DoD
> currently leans on the simulator's one accidental `Unsupported`; with this landed it can drive
> every branch deliberately. Land this first.

### 3.2 A scan you can shape

`DeviceScan` needs more than "one device appears". At minimum: no devices found, one device,
several devices, and a weak-RSSI device. Those are different screens and right now none of them can
be seen.

### 3.3 One wiring point, `__DEV__`-gated

`providers.tsx` is the composition root and already passes no `manager`. Wire the dev manager there
and nowhere else — one file to read, one file to audit, one file to delete when firmware lands.

### 3.4 🔴 Prove it cannot ship

A fake BLE stack in a release build is a device that unlocks without a device. This is the most
dangerous part of the task and needs a real guard, not a comment.

- `__DEV__` gate at the wiring point.
- An **ESLint rule** forbidding any import of the mock from production paths, plus a test that
  proves the rule fires. `tools/lint-guard/__tests__/verificationGuard.test.ts` is the house
  pattern and the reasoning in its header applies verbatim: *"a green check that was never broken
  is not evidence, it's a guess."* Follow its probe-file discipline — write the probe, assert on
  `ruleId`, remove it in a `finally`.
- Confirm a **release** bundle does not contain the mock. `npm run bundle:check` builds dev
  bundles; a `--dev false` bundle plus a grep for a mock-only symbol is the check that actually
  answers this.

## 4. Scope — and where to stop

**In:** the dependency inversion, selectable state, shapeable scan, the `__DEV__` wiring, the guard
and its proof.

**Out, deliberately:**

- **The §4.5 auth handshake running in-app.** That needs a real AES-CMAC/HKDF implementation in the
  bundle, which is its own decision (a JS implementation, or a vetted RN crypto dependency —
  `package.json` is a shared file, announce before adding). It is the natural follow-on and it is
  what unlocks the `LK-*` lock/unlock journey. Scope it separately once this seam exists; note in
  the PR body which flows are blocked on it.
- **The `P1-2.0` gate fix** (`docs/execution-briefs/P1-2.0-bluetooth-unsupported-gate.md`). Related
  and sequenced after this, but a separate diff.
- **Building any `DV`/`LK` screen.** This task makes them buildable; it does not build them.

## 5. Definition of done

- [ ] 🔴 `npm run bundle:check` passes **both platforms** — this is the gate that catches a stray
      `node:crypto` import, and the whole §2 trap lands here
- [ ] 🔴 A release-mode bundle provably does **not** contain the mock (§3.4)
- [ ] The ESLint guard exists **and a test proves it fires** — not merely that it is configured
- [ ] All five radio states drivable in the running app; the existing gate screens observed
- [ ] Scan states drivable: none / one / several / weak RSSI
- [ ] The existing mock-peripheral test suite still passes **unchanged in behaviour** — the
      inversion must not weaken what §4 fidelity the Node tests already prove
- [ ] Real `BleManager` still the default when no manager is injected (`useBleManager`'s lazy
      default is load-bearing — see its comment; do not make it eager)
- [ ] Four gates, no regression from the 2026-08-10 baseline: `typecheck` clean, **537 tests /
      53 suites** (this task should raise it), `lint` 0 errors and **exactly 70 warnings**,
      `bundle:check` both platforms
- [ ] Run it on the simulator and confirm you reach `DeviceScan` with a device listed

## 6. Do not

- **Do not write a second mock under `src/`.** §2.1.
- **Do not guard a `node:crypto` import with `__DEV__`** and assume that works. §2.
- **Do not weaken the mock's §4 fidelity** to make it bundle. If something genuinely cannot cross,
  report it rather than quietly loosening the simulation the UI is being validated against.
- **Do not add an `eslint-disable`.** Baseline is 0 errors / exactly 70 warnings, no suppressions.
- **Do not touch `src/features/auth/**` or `src/features/verification/**`** — unrelated fixes
  landed there today (`9720f8d`).
