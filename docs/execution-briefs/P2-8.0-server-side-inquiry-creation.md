## 2. 🔴 Step 0 — the API key. Not yours to create.

There is **no `PERSONA_API_KEY` anywhere in this repo** — not in `.env`, not in `.env.example`, not
in any function. `PERSONA_WEBHOOK_SECRET` is the *inbound* secret and is a different thing.

**Sadin (or whoever owns the Persona account — this is also OQ-11(b), which is open) must create a
sandbox API key and set it as an Edge Function secret.** Do not create it yourself, do not paste a
key into any file, and do not commit one. `.gitignore` guards `.env`; do not defeat it.

### 🔴 How the key must be scoped — this matters more than it looks

Persona's docs, verbatim: *"Each API key can be configured with specific permissions in order to
limit read or write access to specific API resources"*, under **API > API Keys > Edit > Permissions**
in the dashboard.

**Grant `inquiry.write` and nothing else.**

| Permission | Grant? | Why |
|---|---|---|
| `inquiry.write` — *Create Inquiries* | ✅ **yes** | The only thing this function does. |
| `inquiry.read` — *Read Inquiries* | 🔴 **no** | This is **inviolable rule 1**. `inquiry.read` is precisely the ability to fetch the inquiry payload — name, DOB, ID number, document images. Rule 1 under the Persona architecture is *"never acquire it"*. A key with this permission means the liability we paid a vendor to hold is one API call away from being ours again, and nothing in code would stop a future session making that call. |
| `verification.read` / `verification.write` | 🔴 **no** | Same reasoning, plus write access to verification objects is adjacent to deciding outcomes. |
| everything else | no | Not needed. |

**🔴 The create dialog has no permissions step.** Confirmed in the dashboard on 2026-08-09: *Create
API key* asks only for Name, Note and API version. The key is therefore **born with default
permissions**, and the default on this account is broad — the pre-existing "Default API key" shows
**Full** on Accounts, Cases, Transactions and Verifications. So the order is non-negotiable:

1. **Create** the key (suggested name: `blue-smoke-create-inquiry`).
2. **Immediately** `···` → **Edit** → **Permissions**, and strip it to `inquiry.write` alone.
3. **Only then** copy the value into Edge Function secrets.

Between steps 1 and 2 a broadly-scoped key exists. Do not paste it anywhere during that window.

**Use the Note field** — it is the only thing standing beside the key when a future person decides
whether to widen it, and it lives in the dashboard where that decision gets made, not in this repo:

> `create-inquiry` Edge Function only. **`inquiry.write` ONLY.** Must never be granted
> `inquiry.read` or `verification.*` — Blue Smoke is contractually unable to hold ID images or DOB
> (spec §6.3, inviolable rule 1). Widening this key re-acquires that liability.

Two riders for whoever creates it:

- **Sandbox and production keys are separate objects** ("Each environment has its own API key"),
  exactly like the templates. The production key is a *separate* decision with the same scoping
  question, gated behind the same `PERSONA_ENVIRONMENT` production gate that `min_age` is.
- Persona notes the permission list *"can change at any time and should not be considered to be
  exhaustive"*, so re-read it at creation time rather than trusting this table.

**If the key arrives over-scoped, say so and stop.** Do not proceed on "we just won't call the read
endpoints." Rule 1 is a capability boundary, not an intention.

## 3. What the vendor docs actually say — verified, not guessed

Read from `api-reference/inquiries/create-an-inquiry` on 2026-08-09. This is research, the same
basis on which §6.6 item 1 was closed — it is not the guessing §6.6 prohibits.

```
POST https://api.withpersona.com/api/v1/inquiries
Authorization: Bearer <PERSONA_API_KEY>
Content-Type: application/json

{ "data": { "attributes": { "inquiry-template-id": "itmpl_..." } } }
```

**201 Created** returns:

| Path | What it is |
|---|---|
| `data.id` | `inq_...` — the inquiry id. This is the `inquiry_id` column. 🔴 rule 1 applies to it. |
| `meta.session-token` | **The thing the mobile SDK needs** to continue a server-created inquiry. Without it the app cannot resume the inquiry we just made. |
| `meta.one-time-link` | Hosted-flow URL. We do not use hosted flow; ignore. |

Supported request headers worth knowing: **`Idempotency-Key`** (see §4.3) and `Persona-Version`.

### 🔴 Send `Persona-Version: 2025-12-08` explicitly — do not inherit "Latest"

A Persona API key is created against an API version, and the dashboard's create dialog offers
`2025-12-08 (Latest)`. **"Latest" is a moving label bound to the key, not to our code.** The request
and response shapes above were read from the `2025-12-08` docs, so today the key and this brief
agree — but a replacement key minted later would silently be on whatever "Latest" means then.

Pin it in the request rather than depending on the key's default. The failure this prevents is
**silent, not loud**: a shape change would still return `201`, our parse of `data.id` /
`meta.session-token` would come back empty, and the user would sit on VF-3/VF-4 "still checking"
forever with no error anywhere. Same failure signature as the `serial_hash` salt (OQ-12) and the
`already_decided` path — this project's characteristic bug is the one that returns success.

Pair it with the §5 requirement that a 201 missing `meta.session-token` fails loudly: the header
makes the shape stable, and that check catches it if the assumption ever breaks anyway.

## 4. Decisions already taken — implement these, do not re-open them

### 4.1 Do **not** send `reference-id`

`reference-id` is an optional attribute that would carry our `user_id` to Persona. **We are not
using it**, and this is deliberate rather than an oversight:

- **It is not needed.** The inquiry↔user binding is the `verifications` row this function writes.
  `persona-webhook` already looks up `.eq('inquiry_id', inquiryId)` and returns `404 UNKNOWN_INQUIRY`
  rather than inventing a link — the binding is entirely ours and is stronger for it.
- **It would cost us the §8.3 claim.** That row says a vendor breach is outside our blast radius
  *by design*, because we hold no images and they hold no account of ours. Pushing `user_id` across
  creates exactly the join that sentence says does not exist: their copy of a real person's ID
  documents, labelled with our user id.

If a future task genuinely needs a reviewer to find a case from a support email, the lookup goes
**user_id → our row → inquiry_id**, in our database, where it already works.

### 4.2 Order of operations, and the failure between the two writes

You must call Persona **first** (there is no `inquiry_id` before that), then insert the row. So
there is a window where the vendor call has succeeded and our insert has not.

**Required behaviour:** if the insert fails, return `500` and log the failure **without the
`inquiry_id` and without the `user_id`** (§8.1 — this function holds both at once). The orphaned
inquiry is harmless: no row exists, so when its webhook eventually arrives `persona-webhook` answers
`404 UNKNOWN_INQUIRY` and writes nothing. The user retries and gets a fresh inquiry.

The cost is one wasted billable inquiry. **Take that trade knowingly** — the alternative shapes
(insert a placeholder row first, then patch in the id) fight the unique index on
`verifications.inquiry_id` and the `provider_status = 'pending'` reuse path, and they trade a
harmless orphan for a half-written row that the reuse path would then hand to the next caller.

### 4.3 Concurrency — the reuse path has a race

The existing pending-row reuse (`index.ts`, before the 501) stops a user who backgrounds the app
from minting a second inquiry. It does **not** stop two concurrent requests from both missing the
pending row and both creating one. Persona bills per inquiry, and **OQ-11(b) records that per-user
cost as unowned**, so this is a real cost leak, not a tidiness point.

Use the **`Idempotency-Key`** header. Derive it from something stable per user *per verification
attempt* — do not use the bare `user_id`, or a user who legitimately needs a second attempt after a
decline gets the first inquiry back forever. State your derivation in the PR body; if you cannot find
one you can defend, say so rather than inventing it, and leave the race documented.

## 5. Where the code goes — the house pattern

**There is no Deno on this machine.** You cannot run `supabase functions serve` and you cannot
execute `index.ts`. This is why every testable Edge Function decision in this repo lives in a pure
module under `supabase/functions/_shared/` with tests in `_shared/__tests__/`, run by the
`supabase/functions` jest project — see `personaSignature.ts`, `inquiryTemplate.ts`,
`revokeRequest.ts` for the established shape.

Follow it. Put the request-building and response-parsing in a pure `_shared/` module — something like
`personaInquiry.ts` — and keep `index.ts` as thin wiring around it. Concretely, these must be unit
testable without a network or a Deno runtime:

- building the request body from a template id
- parsing `data.id` and `meta.session-token` out of a 201
- **every non-201 path**: 401 (bad key), 403 (key lacks `inquiry.write` — a very likely first-run
  failure, give it a distinct outcome), 422, 429 (rate limited — `RateLimit-Reset` is in the response
  headers), and a malformed/empty body
- a 201 whose body is missing `meta.session-token` — the app cannot proceed without it, so this
  must fail loudly rather than write a row that strands the user on VF-3/VF-4 forever

**Do not weaken any of this to make a test pass.** If a test is awkward, the test is wrong.
