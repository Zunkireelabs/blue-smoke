## 1. Why this exists

`P1-7.0` is "Connection Lifecycle (Reconnect, **Background Handling**)". Reconnect landed earlier on
this branch. The background half was entirely unbuilt — verified, not assumed: **`AppState` appeared
nowhere in `src/`**, and no native background config exists (`Info.plist` has no `UIBackgroundModes`,
`AndroidManifest.xml` has no `foregroundServiceType` service, there is no restore identifier). The
`P0-4.5` spike that was meant to author that native surface never ran.

Two user-visible consequences today:

1. **`PairDeviceScreen`'s "Open Settings" button strands the user.** They grant the permission in
   Settings, come back, and are still looking at the error screen — nothing re-checks on foreground.
   That is `P1-2.0` item 8, also unbuilt.
2. **A connection dropped while backgrounded is never reconciled** on return.

`connection.ts`'s header also claims "foreground/background state handling — spec §4.9, §7.1", which
it does not do. Fixing that docstring is §3.4.

### 🔴 The rule that shapes the design

**Backgrounding must not disconnect.** It is tidy and it is wrong: the device is kept safe by the
**firmware dead-man timer**, not by this app. Disconnecting on background makes app liveness
load-bearing, which `CLAUDE.md` says to reject on sight. We stop *scanning* — a battery cost with no
safety role — and leave connections alone. This is already implemented that way; do not "improve" it.

### OQ-13 is not in the way

Re-checked directly against `HQD_BLE_Protocol_Commands_Android_EN.md` on Day 10. It adds nothing to
what [`../hardware/hqd-device-architecture.md`](../hardware/hqd-device-architecture.md) §3 already
records. That document's §8 stays authoritative: the block is `BLE_SERVICE_UUID` plus the wire-level
half of §4.5, **and nothing else**. None of this task touches either.

**Coordinator tests — the transition machine:**

| # | Property |
|---|---|
| 1 | Initial phase is `foreground` when `currentState` is `'active'` |
| 2 | Initial phase is `foreground` when `currentState` is `'inactive'` — a launch can observe `inactive`, and that is not the background |
| 3 | Initial phase is `background` only when `currentState` is `'background'` |
| 4 | `active → background` fires `onEnterBackground` exactly once and flips `getPhase()` |
| 5 | `background → active` fires `onEnterForeground` exactly once |
| 6 | 🔴 **`active → inactive → active` fires NEITHER hook** and never leaves `foreground` |
| 7 | A repeated `active` while already foregrounded does **not** re-fire the hook |
| 8 | An unrecognised state (`'extension'`) is ignored, exactly like `inactive` |
| 9 | `dispose()` removes the subscription; a later `emit` fires no hook |
| 10 | `dispose()` twice is a no-op, not a double-`remove()` |

Test 6 is the one that matters most — see the 🔴 block in `appState.ts` for why iOS makes this the
difference between a working app and one that restarts its scan on every notification banner.

**`reconcileConnections` tests — against the real mock:**

| # | Property |
|---|---|
| 11 | A device the manager believes is `connected` but which the radio reports down is reconnected, and its ID is returned |
| 12 | 🔴 That reconnect **re-runs the full §4.5 handshake** — assert the `credentials` `jest.fn` was called a **second** time, the same proof `connection.test.ts` uses. A resumed session would leave it at 1 |

## 5. What this does not prove

- **It does not make background BLE work.** Without the §4 native config, iOS suspends the app and
  the connection drops. That is correct and harmless — the dead-man timer is the authority — but
  nobody may read this PR as "background handling is done."
- **The coordinator is verified against an injected seam, not against iOS or Android.** It proves the
  *policy* is right, not that the OS delivers those events when we think it does. `inactive`
  semantics in particular are asserted from documented behaviour, not observed on a device.
- Nothing here runs on Android at all, or on any physical device.
