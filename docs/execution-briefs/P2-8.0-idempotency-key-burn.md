## 1. The defect, and why it is worse than it looks

`create-inquiry` derives its Persona idempotency key from the user and their attempt count:

```ts
// _shared/personaInquiry.ts:82
buildIdempotencyKey(userId, attemptNumber)  →  `create-inquiry:${userId}:${attemptNumber}`

// create-inquiry/index.ts:175
idempotencyKey: buildIdempotencyKey(userId, attemptNumber ?? 0)
```

`attemptNumber` is the count of that user's `verifications` rows, read **before** the row for this
attempt is inserted. Two facts collide:

1. **Persona binds an idempotency key to the exact parameters of its first use, permanently.**
   Replaying the key with a *different* request body does not return the cached response — it
   returns an error:

   > `400` — *"Keys for idempotent requests can only be used with the same parameters they were
   > first used with. Try using a key other than `create-inquiry:<user>:0` if you meant to execute
   > a different request."*

2. **`attemptNumber` only advances after a SUCCESSFUL Persona call**, because the row is inserted
   after Persona returns (`index.ts` §4.2, deliberately — Persona is called first so a failed
   insert leaves a harmless orphan rather than a half-written row). A call that fails therefore
   never advances the counter, and the next attempt re-derives **the identical key**.

Put together: once a key is burned, that user retries the same dead key forever. There is no
self-healing path, in the app or on the server.

### What burns a key

Any change to the create request body between deploys. This has already happened once: the body
gained `meta: { 'auto-create-inquiry-session': true }` after it was discovered that Persona
otherwise returns `meta.session-token: null` on every 201 (see `personaInquiry.ts`'s module doc).
Every key already used with the pre-flag body is now permanently poisoned.

### 🔴 It is already biting, and it is not theoretical

Verified against the live sandbox on 2026-08-11 — two of the three seeded test numbers **cannot
start verification at all**, and cannot be recovered without changing the key derivation:

| Test number | `attemptNumber` | Result of a create call |
|---|---|---|
| `+1 415 212 7777` | 0 | **`400` Idempotency error → 502** |
| `+1 415 212 7778` | 0 | **`400` Idempotency error → 502** |
| `+1 415 212 7779` | 1 | `201`, session token OK |

In production the same mechanism means: **any future change to the create request body — a new
field, a template swap, a `Persona-Version` bump — instantly bricks verification for every user
with an in-flight attempt at that key, permanently, with no in-app recovery.** A bricked user
cannot verify, and because `age_verified` gates the whole signed-in experience, cannot use the
product.

### The misdiagnosis this causes — fix this too

`400` is not handled by `parseCreateInquiryResponse`. Its ladder covers `401`/`403`/`422`/`429`,
then `if (status !== 201)` sweeps everything else into `unexpected`, which `index.ts` maps to
**`502 PERSONA_BAD_RESPONSE`**.

So a burned key — entirely our own bug, in a request we constructed — presents as *"the vendor
sent us something we couldn't trust."* During this defect's own discovery that reading cost a
full session: it looked like a Persona outage, and Persona was in fact returning `201` with a
valid session token to an identical hand-made call the whole time. **A wrong diagnosis baked into
an error code is worth fixing on its own.**

## 2. The fix

### 2.1 Make the key vary with the request parameters

The key must change when the request changes. Derive it from the user, the attempt, **and a hash
of the exact request parameters being sent** — so a body change automatically yields a new key,
while two concurrent requests for the same attempt still derive the *same* key and still collapse
into one Persona call (which is the property `buildIdempotencyKey`'s existing doc exists to
protect — do not regress it).

Sketch, not a prescription:

```
buildIdempotencyKey(userId, attemptNumber, requestFingerprint)
  → `create-inquiry:${userId}:${attemptNumber}:${requestFingerprint}`
```

where `requestFingerprint` is a short, stable hash (SHA-256, truncated) of the serialised request
body — which today means the template id and the `auto-create-inquiry-session` flag. Deno exposes
`crypto.subtle` in Edge Functions, so no dependency is needed.

**Two properties to preserve, and prove with tests:**

- **Deterministic.** The same user, attempt, and body must always produce the same key — otherwise
  the concurrent-request collapse breaks and Persona bills twice.
- **Sensitive.** Any change to the body must produce a different key. Assert this directly: build
  a key with one body, build another with a changed template id, assert they differ.

A hand-maintained `KEY_VERSION` constant bumped whenever the body changes is an acceptable
alternative and is simpler — but it relies on a human remembering, and the failure mode when they
forget is a permanently bricked user. Prefer the hash; if you choose the constant, say why in the
PR body.

> **Side benefit worth verifying:** changing the derivation gives every currently-burned user a
> fresh key, so `+14152127777` and `+14152127778` should start working again with no data change.
> That is your acceptance test — see §4.

### 2.2 Give the idempotency conflict its own failure kind

Add a distinct `CreateInquiryFailureKind` — e.g. `idempotency_conflict` — for a `400` whose body
identifies an idempotency error, and map it to its own outward status in `index.ts` rather than
letting it hide inside `PERSONA_BAD_RESPONSE`. `CLAUDE.md`'s "handle every result code distinctly,
no generic catch-all" applies squarely here.

Two cautions:

- **Detect it from the response body, not from `400` alone.** Persona may return `400` for other
  reasons; the discriminator is the error title/details naming idempotency. A bare `400` that is
  not an idempotency error should stay `unexpected`.
- 🔴 **Do not echo Persona's error body into our logs or our response.** The existing `detail`
  fields are fixed, safe strings chosen per kind — keep that discipline. Log that an idempotency
  conflict occurred; do not log the key, the user id, or the vendor's message.

### 2.3 What NOT to do

- **Do not retry with a randomised key on conflict.** That defeats the entire purpose of the
  idempotency key — the concurrent-request collapse — and risks minting (and being billed for) two
  inquiries for one attempt. The fix is a key that is *correct up front*, not a retry.
- **Do not advance `attemptNumber` by writing a row on failure.** That inverts `index.ts` §4.2's
  deliberate Persona-first ordering and creates the half-written rows the reuse path would then
  fight over.
- **Do not fall back to creating a fresh inquiry.** Same rule as the resume path: it silently
  doubles the per-verification cost the fixed-price PRD does not contain (OQ-11).

## 5. Worth fixing while you are in here (optional, say either way in the PR)

`create-inquiry/index.ts`'s reuse branch (added by PR #16) ends in a `switch` that is exhaustive
over all seven failure kinds today — but `tsc` does not check this file, so **adding an eighth kind
would silently fall through to `return json(200, { sessionToken: undefined })`**: a success
response carrying no token, which is the exact stranding PR #16 exists to remove. Adding this task's
new `idempotency_conflict` kind makes that eighth kind real. **If you add a kind to the shared
union, you must handle it in every switch over it** — a `default:` returning 502, or a `never`
exhaustiveness check, closes it permanently.
