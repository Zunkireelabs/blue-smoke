## Defect 1 — FW-19's F6 assertion is vacuous (false green)

`tools/mock-peripheral/__tests__/deviceCore.handshake.test.ts`, in
*"FW-19(c) — a framing reset consumes no F6 backoff attempt and does not invalidate N"*:

```ts
for (let i = 0; i < AUTH_BACKOFF.shortThresholdFailures - 1; i += 1) {
```

`shortThresholdFailures` is `5`; `recordAuthFailure` arms backoff at `>= 5`. The loop drives **4**
framing resets, so even if every reset burned an F6 attempt the counter reaches 4 and backoff
never arms. The test cannot fail for the reason it exists.

**Verified, not guessed.** Patching `deviceCore.writeAuthResponseFrame`'s F12 branch to call
`this.recordAuthFailure(this.clock.nowMs())` — i.e. deliberately breaking the obligation the test
names in its own title — left all 56 mock tests **passing**. Changing only the bound to
`i < AUTH_BACKOFF.shortThresholdFailures` made it fail. That one-word change is the fix.

The other half of that test (N not invalidated) is real: mutating the reset to set
`nonceConsumed = true` failed 3 tests. Keep it.

Per v1.8 this assertion is now **FW-19(d)** and covers *both* framing events — rename
accordingly, and drive it with case-(b) duplicates as well as case-(a) stray frame 2s.

## Defect 2 — a repeated frame 1 must REPLACE, not reset (F12a)

`989558e` implements a repeated frame 1 as a full reset. Spec v1.8 §4.5 / F12(a) now requires it
to **replace** the buffered `session_id`/`keyGeneration` and keep awaiting frame 2.

**Why the spec moved rather than the code:** v1.4 contradicted itself — the F12 row said a
repeated frame 1 resets, the FW-19(b) line said it leaves the device awaiting frame 2. The
executor of `989558e` flagged the conflict (correctly) but resolved it toward reset on a
reasoning error: it argued FW-19(c) was unsatisfiable under the replace reading. It is not —
under replace, a later frame 1 replaces again and the following frame 2 still completes.

It was then verified against the mock that the reset reading silently dead-ends the ordinary BLE
retransmit case. Driving `frame 1 → frame 1 → frame 2`:

```
commandResult bytes : 00000000   ← never written
isAuthenticated     : false
```

No result code, no error, app blocked until the nonce TTL. That is the behaviour v1.8 removes.

### Required change — `tools/mock-peripheral/deviceCore.ts`

In `writeAuthResponseFrame`, split the current single mismatch branch:

- `frameIndex === FRAME_1` — **always accepted**, whatever `expectedFrameIndex` is. Overwrite
  `pendingFrame1` with the new `session_id`/`keyGeneration`, set `expectedFrameIndex = FRAME_2`.
  This is the same code path as a first frame 1; there is no separate "duplicate" case to write.
- `frameIndex === FRAME_2` **and** `expectedFrameIndex === FRAME_2` — evaluate as today.
- everything else (a `FRAME_2` with nothing buffered, or any value that is neither `0x01` nor
  `0x02`) — F12(b) reset: discard `pendingFrame1`, `expectedFrameIndex = FRAME_1`, return.

Unchanged and non-negotiable: no branch here writes a `commandResult`, calls
`recordAuthFailure`, or reaches `evaluateHandshake`. `frameIndex` stays **out** of the proof
CMAC.

Keep the `pendingFrame1 === null` invariant throw on the FRAME_2 path — under the rules above it
remains genuinely unreachable.

## Tests

Rewrite the FW-19 block to the v1.8 four cases. `frame 1 → frame 1 → frame 2` must now assert
`ResultCode.OK` — and it must assert the session opened against the **second** frame 1's
`session_id`, not merely that some session opened. Use two *different* session ids; a test that
sends the same `frame1` buffer twice passes under both readings and proves nothing.

Note when asserting "no `commandResult` was written": `ResultCode.OK` is `0x00`, so reading a
result code of `0` is ambiguous with never-written. Compare the whole buffer
(`toEqual(Buffer.alloc(4, 0))`), as the existing tests already correctly do.
