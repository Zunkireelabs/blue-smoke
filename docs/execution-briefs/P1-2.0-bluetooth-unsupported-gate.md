# Execution Brief — the Bluetooth gate hangs forever on a device with no BLE

**Task ID:** `P1-2.0` (defect in the shipped gate) · **Phase:** 1
**Branch:** `fix/P1-2.0-bluetooth-unsupported-gate` — branch off `stage`, push on day one to claim it.
**Size:** small-to-medium. One new leaf screen, one timeout, two doc rows, tests.

---

## 1. The defect, and how it was found

Running the app on the iOS simulator on 2026-08-10: signed in, Home, tap **Pair a device** →
a spinner that never resolves. Left for ~90 seconds. No message, no timeout, no way forward.

**Cause.** `readBluetoothGateState` (`src/features/ble/bluetoothPermission.ts:48`) maps
CoreBluetooth's `Unsupported` to `'unsupported'`. `BluetoothGateScreen` (`:83`) then falls through
to a bare `<ActivityIndicator />` for **all** of `null`, `'unsupported'` and `'unknown'`, under a
comment reading *"a brief spinner is honest about 'still figuring this out.'"*

That is true of `null` and `'unknown'`. It is **false of `'unsupported'`**, which is a final answer:
this phone has no Bluetooth LE radio and never will. We render a terminal state as indefinite
progress.

**Why it matters more than one screen.** Every iOS simulator reports `Unsupported` — there is no
BLE radio in the simulator. So the entire pairing journey (`DV-*`, and everything downstream in
`LK-*`) is **untestable on a simulator today**, and it fails in the one way that teaches you
nothing. With Android never yet compiled and hardware not due until ~Day 26, that currently leaves
the device half of this product with no testable surface at all. Fixing this is partly a UX fix and
partly restoring the team's ability to see its own work.

It also breaks two standing rules: the Definition of Done's *"error states have a user-visible
recovery path"*, and §9's *"every BLE operation has an explicit timeout — no unbounded `await`"*.
The spirit of the second is what is violated here: nothing awaits forever in code, but the **user**
does.

## 2. What to build

### 2.1 `'unsupported'` gets its own terminal screen — **ON-10**

`ON-1`…`ON-9` are taken (`SCREEN_MAP.md`), so **ON-10** is the next free ID. It is a new row in
`SCREEN_MAP.md` and a new entry in `screenSpecs.ts` (which takes the gallery from 41 screens to 42
— expected, not a regression).

Sits alongside the three leaf screens that already exist and follows their shape exactly —
`BluetoothOffScreen.tsx` is the closest template.

**Copy must be honest about there being no fix.** Read `BluetoothOffScreen`'s header comment before
writing a word: its author deleted a "Turn on Bluetooth" CTA precisely because neither the app nor
`Linking.openSettings()` can flip the iOS radio, and shipping a button that cannot do what it says
is the exact failure that comment exists to prevent.

🔴 **So: no "Open Settings" on this screen.** Settings cannot add a Bluetooth radio to a phone that
lacks one. Offering it would be a worse lie than the one already removed.

🔴 **It must not be a dead end.** This project has shipped a screen with no exit three separate
times (`SCREEN_MAP.md`, the VF-2 stranding trap, the two P1-2.0 dead ends). The user's phone
genuinely cannot pair — that is precisely when a way back matters. It is pushed on the Home stack,
so the header back button is a real exit; confirm that by hand rather than assuming, and if the
screen can ever be reached without one, add an explicit action.

Tone: coaching, not diagnostic. Say the phone can't connect to a BlueSmoke device and that
everything else in the app still works. Never print `unsupported`, a CoreBluetooth state name, or
anything a user cannot act on.

### 2.2 `'unknown'` and `null` get a bounded wait

`'unknown'` is genuinely transient (ble-plx's own `Unknown`/`Resetting`), so a spinner is right —
but only for a while. Add a timeout, and on expiry show a **recoverable** state with a working
**Try again** that calls the existing `check()`.

Follow the house convention in `src/features/ble/auth.ts:29-41`: a named constant with a comment
saying it is an app-level choice, not a spec value. Something in the 5–10s range is sensible; say
why you picked what you picked.

Do **not** reuse ON-10 for this. "Your phone has no Bluetooth" and "we couldn't work out the
Bluetooth state just now" are different facts with different recoveries — the same distinction
`SCREEN_MAP.md` already insists on for ON-7 vs ON-8 vs ON-9, and for the same reason.

### 2.3 Leave the rest alone

`poweredOn`, `poweredOff`, `deniedOnce`, `permanentlyDenied` are correct, tested, and out of scope.
Keep the `AppState` foreground re-check working — it is what notices a user flipping the toggle —
and keep `onResolved` firing **only** for `poweredOn`; `DevicePairingGateScreen` `replace()`s to
`DeviceScan` on it.

Preserve the `useCallback` identity discipline in `DevicePairingGateScreen`'s header comment: an
inline arrow as `onResolved` re-fires the resolve effect every render and can loop.

- [ ] 🔴 **Run it on the simulator and see the ON-10 screen instead of a spinner.** This is the
      whole point of the task; the simulator reproduces the bug for free, so there is no excuse for
      not confirming the fix the same way it was found.
- [ ] The `'unknown'`/`null` path resolves to a recoverable screen within the timeout, and
      **Try again** genuinely re-checks (not a dead button)
- [ ] `poweredOn` still resolves through to `DeviceScan`; `poweredOff`/`deniedOnce`/
      `permanentlyDenied` behave exactly as before
- [ ] `AppState` foreground re-check still works (there is an existing test — keep it green)
- [ ] No dead end: a real exit from ON-10, confirmed by hand
- [ ] No CoreBluetooth state name, no diagnostic string, no unusable CTA in any user-facing copy
- [ ] `SCREEN_MAP.md` ON-10 row added; `screenSpecs.ts` entry added (gallery count 41 → 42)
- [ ] Four gates, no regression from the 2026-08-10 baseline: `typecheck` clean, **537 tests /
      53 suites** (this task should raise it), `lint` 0 errors and **exactly 70 warnings**,
      `bundle:check` both platforms

## 5. Do not

- **Do not offer "Open Settings" on ON-10.** §2.1 — it cannot help, and the codebase already
  deleted one CTA for exactly this reason.
- **Do not collapse `unsupported` and `unknown` into one screen.** One is terminal, one is
  transient; that difference is the entire bug.
- **Do not add an `eslint-disable`** to hold the warning count down. The baseline is 70 and the
  rule is no suppressions.
- **Do not touch the auth/verification stacks.** Unrelated fixes landed there today (`9720f8d`);
  keep this diff to the Bluetooth gate.
