## 1. The defect

Found by running the app on the iOS simulator on 2026-08-10: Home → **Pair a device** → a spinner
that never resolved. Left ~90 seconds. No message, no timeout, no way forward.

**Cause.** `readBluetoothGateState` (`src/features/ble/bluetoothPermission.ts:48`) maps
CoreBluetooth's `Unsupported` to `'unsupported'`. `BluetoothGateScreen` (`:83`) then falls through
to a bare `<ActivityIndicator />` for **all** of `null`, `'unsupported'` and `'unknown'`, under a
comment reading *"a brief spinner is honest about 'still figuring this out.'"*

True of `null` and `'unknown'`. **False of `'unsupported'`**, which is a final answer: the device
has no Bluetooth LE radio and never will. We render a terminal state as indefinite progress.

### 1.1 🔴 It no longer reproduces by default — you have to ask for it

`P1-3.0`'s dev fixture supplies a manager reporting `PoweredOn`, so on a simulator the gate now
resolves and you reach `DeviceScan`. **The bug is masked in dev, not fixed.** To see it, set the dev
fixture's radio state to `Unsupported` (`tools/mock-peripheral/devFixture.ts` +
`bleAdapter.ts`'s settable `radioState`).

Do that **first**, before writing anything, and watch the spinner hang. A fix for a bug you have
not personally reproduced is a guess.

### 1.2 Why it still matters now the simulator is unblocked

The original justification — "the whole pairing journey is untestable" — is spent. Two real reasons
remain:

- **`'unsupported'` on real hardware.** Rare on phones, but real: BLE-less Android tablets exist,
  and it is exactly the user for whom an infinite spinner is least explicable.
- **`'unknown'` is the genuine production risk, and it is not rare.** ble-plx emits `Unknown` and
  `Resetting` transiently on real devices at startup and after a stack reset. Today, a transient
  state that fails to settle gives a real user on a real phone a permanent spinner. That is the
  half of this bug most likely to be hit in the wild, and it needs a timeout regardless of what
  `unsupported` does.

It also breaks two standing rules: the Definition of Done's *"error states have a user-visible
recovery path"*, and §9's *"every BLE operation has an explicit timeout — no unbounded `await`"*.
Nothing awaits forever in code here; the **user** does.

## 2. What to build

### 2.1 `'unsupported'` gets its own terminal screen — **ON-10**

`ON-1`…`ON-9` are taken (`SCREEN_MAP.md`), so **ON-10** is the next free ID.

Follows the shape of the three leaf screens that already exist; `BluetoothOffScreen.tsx` is the
closest template.

**Copy must be honest that there is no fix.** Read `BluetoothOffScreen`'s header comment first: its
author deleted a "Turn on Bluetooth" CTA precisely because neither the app nor
`Linking.openSettings()` can flip the iOS radio, and a button that cannot do what it says is the
failure that comment exists to prevent.

🔴 **No "Open Settings" on this screen.** Settings cannot add a Bluetooth radio to a phone that
lacks one. It would be a worse lie than the one already removed.

🔴 **It must not be a dead end.** This project has shipped a screen with no exit three times
(the VF-2 stranding trap, and two P1-2.0 dead ends). The user's phone genuinely cannot pair — that
is exactly when a way back matters. It is pushed on the Home stack, so the header back button is a
real exit; confirm that by hand rather than assuming.

Tone: coaching, not diagnostic. Say the phone can't connect to a BlueSmoke device and that the rest
of the app still works. Never print `unsupported`, a CoreBluetooth state name, or anything the user
cannot act on.

### 2.2 `'unknown'` and `null` get a bounded wait

A spinner is right for these — but only for a while. Add a timeout, and on expiry show a
**recoverable** state with a **Try again** that calls the existing `check()`.

Follow the house convention in `src/features/ble/auth.ts:29-41`: a named constant with a comment
saying it is an app-level choice, not a spec value. Something in the 5–10s range is sensible; say
why you picked what you picked.

Do **not** reuse ON-10 for this. "Your phone has no Bluetooth" and "we couldn't work out the
Bluetooth state just now" are different facts with different recoveries — the same distinction
`SCREEN_MAP.md` already insists on for ON-7 vs ON-8 vs ON-9.

### 2.3 Leave the rest alone

`poweredOn`, `poweredOff`, `deniedOnce`, `permanentlyDenied` are correct and tested. Keep the
`AppState` foreground re-check working, and keep `onResolved` firing **only** for `poweredOn` —
`DevicePairingGateScreen` `replace()`s to `DeviceScan` on it.

Preserve the `useCallback` identity discipline in `DevicePairingGateScreen`'s header comment: an
inline arrow as `onResolved` re-fires the resolve effect every render and can loop.

- **Do not offer "Open Settings" on ON-10.** §2.1.
- **Do not collapse `unsupported` and `unknown` into one screen.** One is terminal, one is
  transient; that difference is the entire bug.
- **Do not "fix" this by changing the dev fixture's default state.** That hides it again. The
  fixture is a test instrument, not the fix.
- **Do not add an `eslint-disable`.** Baseline is 0 errors / exactly 111 warnings, no suppressions.
  *(111, not 70 — `P1-3.0` raised it legitimately; see CLAUDE.md.)*

  beyond reading it and toggling the fixture state locally to reproduce.
