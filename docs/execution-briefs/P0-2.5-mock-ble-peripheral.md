## 3. Scope — build exactly this

A **three-layer** mock. The layering is the point: it is what keeps one implementation of §4 while
letting the transport vary.

```
  Layer 1   deviceCore.ts        pure §4 semantics · no I/O · no timers · no BLE
                 ▲                        tested against RFC 4493 + §4 tables
      ┌──────────┴──────────┐
  Layer 2                Layer 3
  in-process adapter      radio bridge  (spike only, §3.4)
  fake ble-plx API        Swift CBPeripheralManager over a local socket
  → Jest + CI             → physical phone
```

### 3.1 Layer 1 — `tools/mock-peripheral/deviceCore.ts`

**Every §4 semantic lives here and nowhere else.** Transport-agnostic: no BLE types, no sockets,
no `setTimeout`. Its interface is roughly `read(char)`, `write(char, bytes)`, `disconnect()`,
`tick(nowMs)` in, and response bytes plus a notification stream out.

It must implement:

- **Full GATT surface** — C1–C6 byte layouts exactly per §4.2–§4.7, little-endian throughout.
- **§4.5 handshake** — nonce generation, single-use + 30 s invalidation, the mandatory 2-frame
  ordered `authResponse` write (**an out-of-order frame resets the handshake**), HKDF-SHA256
  derivation, constant-time proof comparison.
- **All 7 commands** (§4.6) and **all 10 result codes** (§4.7), each reachable. `CLAUDE.md` forbids
  a catch-all handler; the mock must be able to *produce* every code distinctly.
- **Firmware obligations F1–F11** (§4.8) — locked-by-default on reset, dead-man auto-lock,
  timer-not-cancellable-by-reconnect-alone (**F3**), fail-closed, session expiry, auth backoff,
  connection-scoped command tags (**F11**).
- **Battery model** — drain over time, low-battery flag latching at 15% and clearing at 20% (§4.4).
- **State machine** — `LOCKED` / `UNLOCKED` / `LOCKED_PENDING_ACTIVATION` / `FAULT`, with
  `lastLockReason` and `secondsSinceStateChange` (uint16, saturating at `0xFFFF`).

**Two rules that are load-bearing, not stylistic:**

**(a) Import `src/features/ble/protocol.ts`. Do not redeclare constants.**
A mock that disagrees with the app about a byte offset tests nothing — both sides pass, hardware
fails. Constants §4 needs that `protocol.ts` currently lacks: the **F2 default `autoLockGraceMs`
(5000)**, the **F6 backoff thresholds** (5 failures → 30 s, 10 → 5 min), and the **§4.4 low-battery
latch/clear points** (15% / 20%). **Append** them with `// §4.x` citations — never rewrite an
existing entry. Announce it, per `CLAUDE.md`'s shared-file rule.

**(b) Write your own CMAC. Do not share an implementation with the app.**
`P1-4.0` will need CMAC on the app side. If both sides call the same function, a bug in it cancels
out and the integration test passes green while real hardware fails. **Validate yours against the
RFC 4493 published test vectors** (AES-128 CMAC, the four standard messages) as a unit test. Node's
`crypto` gives you AES-128-ECB to build on and `crypto.hkdfSync` for HKDF-SHA256.

**(c) Inject the clock.** No real timers anywhere. Every time-dependent behaviour — the 30 s nonce
TTL, the 5 s dead-man countdown, 30 s and 5 min backoff, 90-day `sessionExpiry`, battery drain,
`secondsSinceStateChange` — must be driven by an injected monotonic time source so tests advance
time instantly and deterministically. Note §4.5 now specifies **uptime, not wall clock**; model it
that way.

### 3.2 Layer 2 — in-process adapter

A fake implementing the slice of `react-native-ble-plx`'s `BleManager` / `Device` / `Characteristic`
surface the app actually uses, backed by Layer 1. **This is the deliverable that unblocks Phases 1
and 3 on this machine and in CI.**

It must also support **scripted RSSI series** — a caller supplies a sequence of dBm values and the
adapter reports them on `readRSSI()`. §7.2 needs median-of-5 smoothing, a −85 dBm enter-lock
threshold sustained over 3 samples, and −75 dBm exit over 2. Those thresholds belong to the *app*
(`P3-3.0`); your job is only to be able to feed the series that exercises them, including a
boundary-hovering series that must **not** produce flapping.

### 3.3 Failure injection

A control surface — config at construction plus a runtime handle — to force, on demand:

`AUTH_FAILED` · `REPLAY` · `RATE_LIMITED` · `SESSION_EXPIRED` · `NOT_ACTIVATED` · `INVALID_PARAM` ·
`BUSY` · `FAULT` · abrupt disconnect · dead-man expiry · low battery · a scripted RSSI series

If a failure can happen on real hardware, the app must be able to be shown it here. This is the
difference between a mock that proves the happy path and one that proves the product.

### 3.4 Layer 3 — radio bridge · **time-boxed spike, ~90 minutes, report only**

**Do not build this out.** Investigate and report.

Xcode 26.6 is present, so the viable route is a thin Swift `CBPeripheralManager` CLI acting as a
**dumb radio** — it advertises per §4.1, accepts ATT reads/writes, and pipes them over a local
socket to the Layer-1 core. Dumb on purpose: one implementation of §4, in TypeScript, not two.

**Explicitly not `bleno` / `@abandonware/bleno`** — unmaintained, and unlikely to build against
Node 24. Don't burn the timebox proving that.

Report: does it advertise, can a phone discover and connect, and what does macOS `CBPeripheralManager`
*not* let you control (advertising interval, TX power, LESC bonding)? A physical phone is required —
the simulator has no radio.

## 7. Rules that will get this rejected on review

1. **A byte literal that isn't imported from `protocol.ts`.** No magic bytes, anywhere.
2. **Rewriting an existing `protocol.ts` entry** rather than appending.
3. **Sharing a CMAC implementation with the app**, or shipping one not checked against RFC 4493.
4. **A real timer in a test.** It makes the suite slow and flaky and proves less.
5. **A generic catch-all for the 10 result codes** (`CLAUDE.md`).
6. **Implementing `connection.ts` / `auth.ts` / `commands.ts` / `proximity.ts`** — not your task.
7. **Changing §4 to make something easier.** Report the problem instead.
8. **Claiming it works without running it.** If a command fails, report it with the output.
9. **Ticking the physical-device or real-firmware boxes.** They are not achievable here.
10. **Creating a second branch for this task**, or targeting `main` instead of `stage`.

Say so and stop. An honest blocked report beats a mock that looks finished and isn't — this mock is

in a way that a missing one is not.

Specifically worth flagging rather than guessing:

- **§4 is ambiguous about something.** Likely — it has never been reviewed by the firmware team.
  Write down the ambiguity and your interpretation; it feeds the OQ-6 walkthrough.

  test project may need a second Jest config. Report the actual conflict rather than moving the
  mock into `src/` to make it run.
- **`protocol.ts` conflicts with an in-flight BLE branch.** Check `git branch -r` first — it's the
  live claim list — and announce before appending.
