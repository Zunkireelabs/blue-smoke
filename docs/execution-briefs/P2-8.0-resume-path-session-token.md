# Execution Brief — PR A: the reuse path must return a session token (`create-inquiry`)

**Task ID:** `P2-8.0` (defect in the merged backend half) · **Phase:** 2
**Branch:** `fix/P2-8.0-resume-path-session-token` — create it, branch off `stage`.
**Size:** small. One vendor endpoint, mirroring a pattern that already exists in this file.

**Do this before `feature/P2-8.0-app-session-token-handoff`.** That brief's §2.1 explains why; the
short version is that without this fix the app's cancel-then-resume path cannot work at all.

---

## 1. The defect

`create-inquiry` has two success paths and they return different shapes:

```
index.ts:211  fresh   → 201 { inquiryId, sessionToken, templateId }
index.ts:94   reused  → 200 { inquiryId, templateId, reused: true }   ← no sessionToken
```

The reuse path exists for a good reason — Persona bills per inquiry, and a user who backgrounds
the app mid-flow should not mint a second one. But `Inquiry.fromInquiry(id)` **cannot open a
server-created inquiry without a session token**, so as soon as the app switches to consuming this
endpoint, every returning user gets a response they cannot act on.

**Who hits it:** anyone who starts verification, cancels, and taps **Resume** on the VF-5
"Verification paused" screen. A `pending` row already exists by then, so the second call reuses it.
That is the normal path, not an edge case.

Today this is invisible, because the app still creates its own inquiry client-side and never calls
this endpoint on that path.

---

## 2. The fix, verified against Persona's docs — not guessed

`POST https://api.withpersona.com/api/v1/inquiries/{inquiry-id}/resume`

- "Creates a session token that is returned as `meta.session-token`."
- Persona explicitly recommends it: *"When possible, we recommend resuming pending Inquiries
  rather than creating a brand new Inquiry when handling returning users."*
- It also **flips an `expired` inquiry back to `pending`** — useful, and it means resume is the
  right call even for a stale row, not just a fresh-ish one.
- Session tokens are JWTs whose expiry is locked to the inquiry's expiry **at the moment the
  session is created**; later changes to the inquiry's expiry do not extend an existing token.
  Inquiries expire after 24h by default. So mint a token per call — never cache one in our DB.

**Send the same two pinned headers as `buildCreateInquiryRequest`** — `Persona-Version:
2025-12-08` and `Key-Inflection: kebab`. The kebab pin is not optional: the response key is read as
`meta['session-token']`, and a Camel flip silently makes it `sessionToken` and the parse returns
`undefined` with no error anywhere. This is the same trap documented in `personaInquiry.ts`'s
module header, and it applies identically here.

### ⚠️ The one unknown — check it, don't assume it

The sandbox API key was deliberately narrowed to **`Create inquiries` only** on 2026-08-10
(`session-log/sadin.md` — a new Persona key is born with every permission ticked, including ones
that breach rule 1). **Whether that scope covers `/resume` is unverified**; Persona's public docs
do not state which permission governs it, and the hint they do give suggests resume may be an
inquiry *action* rather than a create.

You do not need to resolve this before starting. The existing failure mapping already handles it:
a `403` surfaces as `PERSONA_FORBIDDEN` with a distinct, safe log line. **If you get a 403 on
resume, stop and report it** — the fix is Sadin ticking one more permission in the dashboard, and
it is his action, not yours (brief §2 of the original P2-8.0 task, "not yours to create").

**Do not work around a 403 by falling back to creating a fresh inquiry.** That silently doubles the
per-verification cost the fixed-price PRD does not contain (OQ-11), and it is exactly the kind of
quiet degradation this project keeps finding months later.

## 3. Where the code goes

Same split as the rest of this feature — pure logic in `_shared`, thin glue in `index.ts`.

**`supabase/functions/_shared/personaInquiry.ts`** (append; do not restructure what is there):

- `buildResumeInquiryRequest({ apiKey, inquiryId })` → `PersonaHttpRequest`. Reuse the existing
  interface. Same pinned headers. **No `Idempotency-Key`** — resume is not the operation the
  idempotency key exists to deduplicate, and reusing `buildIdempotencyKey`'s value here would
  collide with the create call's key for the same attempt.
- `parseResumeInquiryResponse({ status, rawBody })` → reuse `CreateInquiryFailureKind` and the
  same never-throws discipline. A `200`/`201` whose `meta['session-token']` is absent is
  `missing_session_token`, exactly as on the create path. Confirm which status resume actually
  returns from the live call rather than assuming `201`.

**`supabase/functions/create-inquiry/index.ts`** — the reuse branch at `:93`:

```
if (pending?.inquiry_id) {
  → call resume for pending.inquiry_id
  → on success: 200 { inquiryId, sessionToken, templateId, reused: true }
  → on failure: the SAME distinct status mapping the create path already uses (:140–:159)
}
```

Keep `reused: true`. It is honest and the app can use it; the point of this change is that
`sessionToken` is now present on **both** shapes, so the client has one contract.

🔴 **Do not let this branch touch `age_verified`.** It stays untouched on this path — the row
already exists and only `persona-webhook` may decide it. Grep the diff.

🔴 **Neither `inquiry_id` nor `user_id` in any log line**, including the new failure path. The
function holds both right there. Follow the existing comments at `:196` and `:205` — log
`.message` only, never a Postgres `DETAIL` line.

## 5. Do not

- **Do not touch `persona-webhook`.** Its `already_decided` path (`index.ts:199`, `:214`) is a
  known parked defect with its own task.
- **Do not cache a session token in the database.** §2 — its expiry is locked to the inquiry's, so
  a stored token goes stale silently. Mint per call.
- **Do not send `reference-id`** on any request, here or anywhere (original brief §4.1).
- **Do not fetch the inquiry payload** from Persona's API, including as a debugging convenience.
