## 1. What this task is

The app still creates its own inquiry:

```ts
// PersonaVerificationScreen.tsx:56
Inquiry.fromTemplate(config.templateId).environment(config.environment)…build().start()
```

Spec §6.2 calls that shape one that **cannot be secured** — the client picks its own inquiry and
nothing binds it to a user server-side. `create-inquiry` now mints the inquiry, writes the
`pending` row that *is* the inquiry↔user binding, and returns a session token. This task moves the
app onto it.

**It is one screen and one hook's worth of change, and three traps.** The traps are the task; the
mechanical swap is twenty minutes. Read §3 and §4 before writing anything.

## 2. The contract you are consuming — read the real thing, don't infer it

`supabase/functions/create-inquiry/index.ts`. `POST`, no body, caller's JWT required
(`verify_jwt: true`, so Supabase rejects an unauthenticated call before our code runs).

**Two success shapes, and they are not the same shape.** This is trap #1.

| Path | Status | Body |
|---|---|---|
| Fresh inquiry (`index.ts:211`) | `201` | `{ inquiryId, sessionToken, templateId }` |
| **Reused pending inquiry** (`index.ts:94`) | `200` | `{ inquiryId, templateId, reused: true }` — **no `sessionToken`** |
| Post-race loser (`index.ts:202`) | `201` | `{ inquiryId, sessionToken, templateId }` |

Failure bodies, each distinct and each needing its own handling (§5): `401 UNAUTHENTICATED`,
`401 PERSONA_UNAUTHENTICATED`, `403 PERSONA_FORBIDDEN`, `422 PERSONA_UNPROCESSABLE`,
`429 PERSONA_RATE_LIMITED` (with optional `retryAfterSeconds`), `502 PERSONA_BAD_RESPONSE`,
`500 NOT_CONFIGURED`, `500 LOOKUP_FAILED`, `500 INSERT_FAILED`, `405 METHOD_NOT_ALLOWED`.

### 🔴 2.1 The reuse path returns no session token, and you cannot resume without one

This is a **real gap in the backend**, found while writing this brief, not a thing you can code
around in the app. `Inquiry.fromInquiry(id)` without `.sessionToken(...)` cannot open a
server-created inquiry.

Verified against Persona's own documentation on 2026-08-10 (not inferred):

- `POST https://api.withpersona.com/api/v1/inquiries/{inquiry-id}/resume` "creates a session token
  that is returned as `meta.session-token`."
- Persona explicitly recommends this: *"When possible, we recommend resuming pending Inquiries
  rather than creating a brand new Inquiry when handling returning users."*
- Session tokens are JWTs whose expiry is **locked to the inquiry's expiry at the moment the
  session was created**; changing the inquiry's expiry afterwards does not extend an existing
  token. Inquiries expire after 24h by default.

**So the reuse path must call `/resume` and return a fresh `sessionToken`, exactly like the fresh
path does.** That is a `create-inquiry` change, in `_shared/personaInquiry.ts` + `index.ts`.

> **Decision for Sadin, not for the implementer.** This makes the task span two areas, which
> CLAUDE.md says to split. Recommended split: **PR A (backend)** teaches the reuse path to
> `/resume`, so both paths return the same shape; **PR B (app)** consumes one uniform contract.
> Doing B first means building the client against a response shape that strands every returning
> user — see §3.2 for exactly who gets stranded. **Do not start B until A has landed**, or the
> app's happy path will look fine and its second-attempt path will be dead.
>
> A also needs a Persona permission check: the sandbox key is currently scoped to **`Create
> inquiries` only** (deliberately narrowed on 2026-08-10 — see `session-log/sadin.md`). Whether
> `/resume` is covered by that scope or needs another one is **unverified**. Find out before
> assuming; a `403 PERSONA_FORBIDDEN` on resume is the expected symptom if it is not.

## 3. The three traps

### 🔴 3.1 The `pending` row now means two different things

`create-inquiry` writes `provider_status = 'pending'` **at inquiry-creation time — before the user
has scanned anything.** `useVerificationStatus.ts:toState()` maps that row to `'pending'`, and
`navigation.tsx:141` maps `'pending'` to its own single-screen stack ("Confirming your
verification…").

Today that collision is invisible, because today no row exists until the webhook lands. **After
this change, the row exists from the moment the user taps Start.**

So the moment anything refetches the verification query while the Persona modal is open, the
navigator **tears down the `VerifyAge` stack underneath the native modal**. The modal itself
survives — it is a native presentation, not an RN view — so the user keeps scanning, their
`onComplete`/`onCanceled` callbacks fire into an unmounted component, and when they dismiss the
modal they land on "Confirming your verification…".

For a user who *completed*, that is accidentally the right screen. **For a user who cancelled, it
is a stranding trap**: they cancelled, and they are now parked on a screen that says we are
confirming their submission, polling every 5s for a webhook that will never arrive, with no
Resume, no "Do this later", and no way back. That is precisely the VF-2 class of bug this project
has already shipped three times (`SCREEN_MAP.md`, reproduced on a real device 2026-08-09).

**Why it does not already fire today, and why that is fragile:** `refetchInterval` only polls when
the data is *already* `'pending'` (`useVerificationStatus.ts`), `QueryClient` is constructed bare
in `providers.tsx` with no `focusManager`/AppState wiring, and the hook is mounted once in
`RootNavigator` and never remounts. So nothing currently triggers that first refetch — which is
also the known "restart required to see a verification land" defect from 2026-08-09.

**The tempting fix is the bug.** Invalidating `['verification-status']` after calling
`create-inquiry` is the obvious way to close the restart-required gap — and it is exactly what arms
this trap.

**Do this instead:** the navigator must not swap stacks while a capture is in flight. Hold a
"capture in progress" flag (a small Zustand store, matching the house pattern in
`src/app/stores/`), set before `.start()` and cleared in *every* terminal callback —
`onComplete`, `onCanceled`, `onError` — and have `selectStack` refuse to leave the verification
stack while it is set. Clearing it in all three is the whole point; clearing it only in
`onComplete` re-creates the trap for the cancel path.

`selectStack` is a pure function with existing tests (`src/app/__tests__/navigation.gating.test.tsx`)
— extend those. **Rule 3 is not weakened by this**: the flag only defers *which screen shows*, and
`'verified'` still comes solely from server state. It must never be able to route anyone *to* Home.

### 3.2 Who actually hits the reuse path

Not a rare edge. The gate sends `'none'` and `'declined'` users into the verification stack
(`navigation.tsx:147`). A user who starts, cancels, and taps **Resume** on the VF-5 "Verification
paused" screen calls `launch()` again on the same mounted screen — and by then a `pending` row
exists, so the second call takes the reuse path and gets no session token. **Cancel-then-resume is
the normal path**, and it is the one §2.1 breaks. This is why PR A comes first.

### 3.3 `InquiryBuilder` is not `TemplateBuilder`

Verified against the **installed** typings — `react-native-persona@2.49.0`,
`lib/typescript/index.d.ts` (note: `TODO-phase-2.md` records the `^2.7.0` *range*; 2.49.0 is what
is resolved):

- `Inquiry.fromInquiry(inquiryId): InquiryBuilder` — line 133, the **class static**, current API.
  The deprecated `fromInquiry` is the namespace-level one at line 262, whose own deprecation notice
  says to use the class static. Use `Inquiry.fromInquiry(...)`.
- `InquiryBuilder.sessionToken(token): InquiryBuilder` — line 175.
- **`InquiryBuilder` has no `.environment()`** (compare `TemplateBuilder`, line 225). The
  environment is a property of the inquiry, which the server created against a sandbox or
  production key. `getPersonaConfig()` therefore becomes vestigial on this path — `templateId` now
  comes from the response, and environment is not ours to set. Do not delete it in this PR if
  anything else still reads it; say so in the PR body either way.
- `InquiryBuilder` also has **no `.referenceId()`**, which enforces brief §4.1 (never send
  `reference-id`) at the type level. Good — leave it that way.
- Callback signatures (`lib/typescript/callbacks.d.ts`) differ from what the screen assumes today:
  `OnCompleteCallback = (inquiryId, status, fields, extraData) => void` and
  `OnCanceledCallback = (inquiryId?, sessionToken?) => void`.

> 🔴 **Take nothing from `onComplete` beyond the fact that it fired.** `fields` and
> `extraData.collectedData` are vendor-side capture data — inviolable rule 1 says we never acquire
> it. Do not read them, do not log them, do not put them in state. `status` stays a UI hint
> (CLAUDE.md verification rule 2). The existing screen already gets this right by taking no
> arguments at all; keep that.

**Keep the modal `.start()` path.** Do not switch to `<PersonaInquiryView>` — it is registered
with `requireNativeComponent` and hard-crashed on mount under the New Architecture (P2-1.0; the
reasoning is in `PersonaVerificationScreen.tsx`'s header comment, lines 29–37). That comment stays
true and stays.

## 4. Where the code goes

House pattern, same split as the backend half: pure logic separated from the component.

- **`src/features/verification/createInquiry.ts`** *(new)* — calls the Edge Function, parses and
  narrows the response into a discriminated union, maps every §2 failure body to a distinct
  outcome. Pure enough to unit-test without a component. **There is no existing
  `functions.invoke` call anywhere in `src/`** — this is the app's first one, so there is no house
  precedent to copy; establish a clean one.
- **`src/features/verification/PersonaVerificationScreen.tsx`** — `launch()` becomes async: call
  `create-inquiry`, then `Inquiry.fromInquiry(inquiryId).sessionToken(token)…build().start()`. The
  existing `starting` / `pending` / `canceled` / `error` / `not_configured` stages and the VF-2
  stranding fix (`autoStarted` gating only the one automatic launch) all stay exactly as they are.
- **`src/app/stores/`** *(new store)* — the capture-in-progress flag from §3.1.
- **`__mocks__/react-native-persona.js`** — ⚠️ shared file, announce it. `Inquiry.fromInquiry`
  currently returns a `TemplateBuilder` with **no `sessionToken` method**, so the first test that
  exercises the real call path will throw `TypeError: .sessionToken is not a function`. Add a
  proper `InquiryBuilder` mock. Keep `__lastHandlers()` working — existing tests depend on it.

Every network call needs an explicit timeout (CLAUDE.md — "no unbounded `await`"). That rule is
written for BLE but the reason applies here: a hung `create-inquiry` leaves the user on
"Starting verification…" forever.

## 5. Failure modes — each needs a distinct, tested outcome

No catch-all. The user-facing text is **coaching, never diagnostic** (CLAUDE.md): never show an
error code, never show a vendor status string.

| Outcome | User sees | Recovery |
|---|---|---|
| `401 UNAUTHENTICATED` | session expired | route to sign-in |
| `401`/`403`/`422`/`502` (vendor/config) | "we can't start verification right now" | Try again + sign out |
| `429` | "give it a moment" | honour `retryAfterSeconds` if present |
| `500 NOT_CONFIGURED` | the existing `not_configured` stage | as today |
| Network failure / timeout | transport failure, **not** a decline | Try again — reuse `TransportErrorScreen`'s framing (F6.X / VF-7) |
| `200 reused` with no `sessionToken` | — | **after PR A this must be unreachable.** Until then, treat it as a hard error rather than silently starting an inquiry that cannot open. Never `.start()` without a token. |

The last row matters most: a missing token must fail **loudly**. The backend already takes this
position (`missing_session_token` → `502`, `personaInquiry.ts:95`) precisely so the app is never
handed a row it cannot resume. Do not be more permissive than the server.

## 6. Scope — and where to stop

**In:** the client swap, the capture-in-progress flag, the mock, the tests.

**Out, each with a reason:**

- **`persona-webhook`.** Untouched. Its `already_decided` path (`index.ts:199`, `:214`) is a known
  parked defect with its own task — not to be "tidied" here.
- **The `pending`-means-two-things problem, solved properly.** A `provider_status` that
  distinguishes *inquiry created* from *user submitted* is the clean fix and it is a **migration**
  — append-only, announce first, and out of scope. §3.1's flag is the app-side containment.
- **The restart-required refetch gap.** Related and tempting; it is what makes §3.1 dangerous.
  Land the flag first, then close it deliberately.
- **VF-11 / manual review.** Still blocked on OQ-2 (no owner, channel, or SLA). Do not wire a
  "Get help" button to nothing — that is the bug this project has shipped three times.

## 8. Do not

- **Do not start this before PR A (§2.1) lands.** The happy path will pass and every returning
  user will be dead.
- **Do not invent the resume endpoint's request shape.** §2.1's URL and `meta.session-token` key
  are verified against Persona's docs; the request body and required key scope are **not**. Check,
  or ask. A guessed value here fails silently, the same way `min_age` and `Key-Inflection` did.
- **Do not read the inquiry payload from Persona's API**, as a debugging convenience or otherwise.
- **Do not switch to `PersonaInquiryView`** (§3.3).
- **Do not weaken `selectStack`'s ordering** to make the flag work. `'verified'` must stay the only
  route to Home.
