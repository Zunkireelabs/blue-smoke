## 1. What this task is, and the one decision that shapes it

Hardik built email auth as **6-digit codes instead of magic links**, proven end to end against
real Supabase. He also **deleted passwords entirely**. We are taking the codes and **keeping
passwords** — the two are separable, and his own reason for removal was a UX problem, not a
capability one:

> *"Keeping two email methods side by side turned out to be the unstable half: one of them had a
> password field and one did not, and **only one could be the front door**."*

That is solved by making password a **later credential**, not a competing entry point:

- **One front door, always:** email → 6-digit code. There is never a second email signup path,
  so the instability he hit cannot arise.
- **The code IS the recovery.** Forgot your password? Sign in with a code and change it in
  Settings. So we keep passwords *and* delete the whole reset subsystem.
- Nothing is removed that the client confirmed, so this is **not blocked** on the outstanding
  client sign-off that Hardik's full removal would need.

**PR 1 (this task)** lands the code-based email auth and deletes the password *screens* and the
reset flow, while **keeping the password client methods intact but unrouted**.
**PR 2 (separate, later)** adds *Set a password* in Settings and *Use password instead* sign-in.
