**Prerequisite:** none — everything this touches has already landed

---

## 1. Why this exists

`P1-3.0` (scan & discovery) and `P1-7.0` (connection lifecycle) landed on Day 10 with 355 passing
tests. Every suite tests **one unit in isolation**: `scanner.test.ts` proves scanning,
`connection.test.ts` proves reconnect, `PairDeviceScreen.test.tsx` proves the screen.

**Nothing walks the full path.** A break *between* those pieces — a scan result whose shape the
connection manager can't consume, a state transition that strands the UI — passes every existing
test. And the suite's only output is a green count; there is no artefact a human can read to see
what the stack does.

This brief adds one suite that walks the whole chain in a single continuous run and narrates it in
plain language while it does. CI enforces the chain; a person can read the transcript.

**No new dependencies.** Jest is the runner and the test file is the transcript.

### 3.2 `src/features/ble/__tests__/journey.test.ts` — new, the deliverable

One `describe`, a series of `test()`s **run in order**, sharing state built once in `beforeAll` —
a single `createMockPeripheral()` and `FakeClock`. Deliberately **not** independent-per-test: the
chain is the point. Say so in a comment, because it violates the usual isolation instinct.

#### Transcript mechanics

Narrate with **`process.stdout.write`**, not `console.log` — Jest prefixes console output with
`console.log` headers that wreck the reading experience; direct stdout writes come through clean.
Use a small local `say(line: string)`.

Target output a non-programmer can follow end to end:

```
  Bluetooth is switched off — the app reports "bluetoothOff", not a crash
  Bluetooth on. Scanning…
  Found 2 devices: mock-device-0001 (-55 dBm, battery 77%), mock-device-0002 (-70 dBm)
  Same device advertises again — still 2 in the list, seen 2x
  Connecting to mock-device-0001…
  Connected, handshake passed (credentials requested 1x)
  Link dropped abruptly — no goodbye, like walking out of range
  Reconnecting… connected, and the handshake ran AGAIN (credentials requested 2x)
  A device offering the wrong key is rejected: AUTH_FAILED
```

#### The journey

Every API below already exists. Reuse; do not reinvent.

| # | Drive | Assert |
|---|---|---|
| 1 | `manager.setAdapterState('PoweredOff')`; `createDeviceScanner({scanner: manager})`; `.start()` | `getState()` → `{status:'blocked', reason:'bluetoothOff'}` |
| 2 | `manager.setAdapterState('PoweredOn')` | `status:'scanning'` |
| 3 | advertisements arrive via `startDeviceScan` | both devices present, **discovery order** stable, primary's `advertisement` parsed (`protocolVersion`, `batteryPercent`, `stateHintRaw`, `flagsRaw`) |
| 4 | `manager.emitAdvertisement(device)` | list length **unchanged**; that device's `advertisementCount` incremented |
| 5 | `scanner.stop()`; `createConnectionManager({manager, credentials})`; `.connect(DEVICE_ID)` | `connecting` → `connected`; `credentials` called **once**; `getLastFailure()` is `null` |
| 6 | `device.simulateAbruptDisconnect()` | state → `reconnecting` |
| 7 | `await jest.advanceTimersByTimeAsync(1000)` | state → `connected`; `credentials` called a **second** time |
| 8 | a *separate* `createConnectionManager` using `wrongCredentials()` | `getLastFailure()` → `{stage:'handshake', outcome:{ok:false, resultCode:0x02}}` |

**Step 7 is the load-bearing assertion: a session never survives a disconnect.** A session-reuse bug
leaves the call count at 1 and every other assertion still passes. Comment it as such.

#### Setup specifics

```ts
createMockPeripheral({
  kDev: K_DEV,
  clock: new FakeClock(0),
  deviceId: 'mock-device-0001',
  advertisedRssi: -55,
  manufacturerData: /* 4 bytes — see below */,
  additionalAdvertisers: [{ id: 'mock-device-0002', name: '…', advertisedRssi: -70 }],
})
```

- Build the 4-byte manufacturer data from `ADVERTISING_MANUFACTURER_DATA_OFFSETS`, copying the
  `buildManufacturerData()` pattern at `scanner.test.ts:36-45`. **Fixture rule (inherited from the
  `P1-4.0` brief §5): every byte a distinct value**, so a wrong offset cannot produce a passing
  assertion.
- `additionalAdvertisers` entries share the primary's `DeviceCore` but **cannot be connected to** —
  `MockBleManager.assertKnownDevice`, `bleAdapter.ts:311`. Connect only to the primary. This is the
  mock's honest model of "discovered, not connectable".
- `MockDeviceOptions` is `{id, name, rssiSeries?, advertisedRssi?, manufacturerData?}`
  (`bleAdapter.ts:39`).

#### Timers — the one real trap

`jest.useFakeTimers()` in `beforeAll`, `jest.useRealTimers()` in `afterAll`, mirroring
`connection.test.ts:55-61`.

Both modules use the **global** `setTimeout`: the scanner's 15 s scan timeout (`scanner.ts:328`) and
the connection manager's backoff. Advancing 1000 ms at step 7 leaves the scan timeout pending across
the rest of the run. **Call `scanner.stop()` at step 5** — realistic (you stop scanning once you have
picked a device) and it clears the timer.

Both modules also accept injection if you need it — `scanTimeoutMs`/`now` (`scanner.ts:128-134`),
`setTimeoutFn`/`clearTimeoutFn` (`connection.ts:63-65`). **Prefer `stop()`:** it exercises real
behaviour rather than configuring the problem away.

### 3.3 tsconfig registration — mandatory, not optional

Any test importing `createMockPeripheral` needs `Buffer`/`node:crypto`, which the root program's
`"types": ["jest"]` deliberately excludes so app code cannot gain `Buffer`. The established pattern —
documented at length in both files, with five existing precedents — adds the file to **both**:

- `tsconfig.json` → `"exclude"`, with a one-line comment matching its neighbours
- `tsconfig.test.json` → `"include"`

Miss either and `npm run typecheck` fails. **Do not "fix" that by widening root's `types`.**

## 5. What this test does not prove

State this in the commit body. Do not let it be overclaimed anywhere else either.

Per `tools/mock-peripheral/README.md:116`, layers 1–2 prove **"our §4 logic is right"**, not
**"BLE works."** No `react-native-ble-plx`, no iOS/Android BLE stack, no LESC bonding, no
connection-parameter negotiation, no advertising, no background execution.

🔴 **It cannot validate `BLE_SERVICE_UUID`.** That constant is **OQ-13** — invented at spec-writing
time (commit `0bb8e80`, 2026-08-05) and unconfirmed against hardware, which per
`docs/hardware/hqd-device-architecture.md` §2 probably describes a GATT layout the device's YC1012
does not present at all. The scanner filters on it and the mock advertises it, both reading the same
constant, so **the filter matches by construction.** This suite validates everything *downstream* of
that UUID and nothing about the UUID itself.

## 9. If you get stuck

| Symptom | Cause |
|---|---|
| A journey step needs an API that doesn't exist | §4 — stop and report. Missing seam > missing test |
| `typecheck` fails on `Buffer` / `node:crypto` | §3.3 — you missed one of the two tsconfigs |
| Backoff won't advance | Use `advanceTimersByTimeAsync`, not the sync version — the connection manager awaits promises between timer fires |
| Scan timeout fires mid-journey | §3.2 — you skipped `scanner.stop()` at step 5 |
| Lint warnings above 70 | Fix the code. Adding `eslint-disable` to hold the number down is a breach |
| `connectToDevice` throws "unknown device" | You tried to connect to an `additionalAdvertisers` entry. Only the primary is connectable |
