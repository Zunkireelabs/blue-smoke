# Execution brief — P0-7.0 follow-up: contrast-pair completeness guard

**Base:** `chore/integrate-auth-db-persona` @ `7a8d006`, **with the P0-7.0 working tree in place**
(the design system is uncommitted and partly untracked — do not discard it, and commit it as
part of this work).
**Prior brief:** `docs/execution-briefs/P0-7.0-design-system-token-first.md`
**Scope:** `src/shared/ui/**` only.

## The defect

`contrastPairs` in `tokens.ts` is a hand-maintained list, and two semantic colour tokens that
components actually render are absent from it:

- `Card.tsx:10` — `backgroundColor: tokens.color.surface`
- `Text.tsx:43` — `color: tokens.color.textInverse`

Verified by mutation: degrading `surface` to `neutral[400]` leaves **54/54 passing**. Degrading
`textInverse` to `neutral[400]` leaves **54/54 passing**. The control mutation (`textSecondary`,
which *is* in the list) fails correctly, so the contrast test works — it is simply not being
asked about these two.

**This is not a live bug.** `surface` and `textInverse` are currently both `neutral[0]`,
numerically identical to `background` and `interactivePrimaryText`, which are covered. They are
covered by coincidence of value, not by construction.

**Why it still matters:** that coincidence ends at the OQ-7 reskin. The moment `surface` becomes
a tinted card background distinct from the page, the contrast suite silently stops covering the
component that uses it — during the exact operation this task exists to make safe. `tokens.ts`'s
own comment says "Add a pair here when a component introduces a new one", which is precisely the
manual step that gets skipped.

## Required change

Do **not** simply add two entries to `contrastPairs`. That fixes today's two and leaves the next
token exposed to the same failure. Make the list impossible to under-populate.

Add a **completeness guard** test in `src/shared/ui/__tests__/`:

1. Scan `src/shared/ui/**` and the restyled screens (`PhoneInputScreen.tsx`, `OtpEntryScreen.tsx`)
   for `tokens.color.<name>` / `color.<name>` references — reuse `sourceFiles.ts`, which already
   does exactly this walk for the token-only and dynamic-type guards.
2. Classify each reference as foreground (`color:`, icon/text tint) or background
   (`backgroundColor:`).
3. Assert every referenced colour appears in at least one `contrastPairs` entry, on the matching
   side (a token used as a background must appear as some pair's `bg`; as a foreground, some
   pair's `fg`).
4. Then add the pairs needed to make it pass — `textPrimary on surface` and `textInverse on
   interactivePrimaryBackground` at minimum, plus whatever else the scan surfaces.

Tokens that are legitimately not a text surface (`border`, `borderStrong`, `dangerBorder`,
`focusRing`) need an explicit, named exemption list in the test — not a silent filter. Each
exemption carries a one-line reason. An exemption list that is easy to grow is the same defect
again, so keep it to genuinely non-text roles.

## Traps

- The scan is regex over source text. `tokens.color.surface` and a destructured
  `const { color } = tokens; color.surface` are different strings — handle both, or assert that
  the destructured form does not appear in the scanned files.
- Do not assert a precomputed contrast ratio anywhere. The existing `contrast.test.ts` computes
  from the WCAG formula; keep it that way.
- No snapshot tests.
