## 3. Finding 6 🟠 — the `commandId` guard is untested, and it now carries more weight than it did

### What is wrong

`auth.ts:243-247`:

```ts
if (commandId !== HANDSHAKE_RESULT_COMMAND_ID) {
  // Something unrelated wrote to this characteristic (e.g. an
  // in-flight lockCommand result) — not this handshake's answer.
  return;
}
```

Deleting this guard entirely: **14 passed, 0 failed.** Nothing in the suite holds it.

### Why it matters more after `3d15000` than before

This is the part worth reading twice. The previous brief's finding 5 changed the fall-through
behaviour of the notification handler:

| | stray notification with a non-OK code | |
|---|---|---|
| **before `3d15000`** | fell out of the handler, ignored | handshake continued, then timed out |
| **after `3d15000`** | resolves `unexpected-result-code` | **handshake terminates on another command's result** |

So the guard went from "avoids a redundant no-op" to "the only thing standing between an in-flight
`lockCommand` result and a wrongly-terminated handshake" — and it acquired that role in the same
commit that left it unpinned. A correct fix quietly raised the cost of a future regression elsewhere.
That is exactly the kind of coupling a test has to record while someone still remembers it.

### The fix — one test

Drive **two** notifications through the real listener, in order:

1. a stray one with a `commandId` that is **not** `HANDSHAKE_RESULT_COMMAND_ID`, carrying a
   result code that *would* change the outcome if it were accepted — use `FAULT` (0x08), so a
   removed guard produces `unexpected-result-code` rather than something ambiguous;
2. the genuine handshake result.

Assert the outcome comes from (2) and shows no trace of (1).

Use the manager-double style already established by the `faultManager` test at `auth.test.ts:362` —
that double already captures the listener and fires it from inside a write, which is the mechanism
you need. **Do not** add a failure-injection surface to `deviceCore.ts`; the mock's handshake path
cannot produce these codes by design and that is not this brief's problem to solve.

**Mutation it must kill:** delete the `if (commandId !== HANDSHAKE_RESULT_COMMAND_ID) { return; }`
block. Paste both runs.

## 4. Finding 7 🟡 — the `resolveOnce` settled-once guard is untested

`auth.ts:226-232` — `resolveOnce` ignores every call after the first. Removing the `if (settled)`
early return: **14 passed, 0 failed.**

The guard is not decorative. §4.5's `commandResult` is a notification, and a device that notifies
twice (a retransmit, or a duplicate delivered by the stack) is an ordinary event, not an exotic one.
The `Promise` itself already ignores a second `resolve`, so today the guard is belt-and-braces — but
the moment `settleResult` becomes anything other than a bare promise resolver (a callback, a state
machine transition, a Part 2 store dispatch), the guard becomes the only thing preventing a double
transition, and nothing will fail if it has been dropped by then.

### The fix — one test

Fire the listener **twice** with two *different* result codes — e.g. `OK` then `FAULT`, so the
outcomes are unambiguously distinguishable. Assert `authenticate()` resolves to the **first**.

**Mutation it must kill:** remove the `if (settled) { return; }` early return. Note the honest
subtlety: with a bare promise resolver, that mutation may still not fail. **If it does not, say so
in the report and leave the test in** — record it as pinning intent rather than behaviour, and do
**not** manufacture a fake failure by changing `auth.ts` to make the test bite. A test that
documents a currently-unfalsifiable property is worth having; a production change made to justify a
test is not.

## 5. Finding 8 🟠 — `subscription?.remove()` is untested; a leak is invisible

`auth.ts:327-330` — the `finally` that unsubscribes. Replacing the body with a comment: **14 passed,
0 failed.**

A leaked `monitorCharacteristicForService` subscription per handshake attempt is a real cost on a
long-lived `BleManager`: the listener stays attached to the characteristic, and after the
rate-limiting path (five failures, §4.8) there are six of them. It also fires on every subsequent
device notification for the life of the connection. None of this is visible to the suite.

### The fix — one test (two assertions), covering both shapes

1. **Subscription created, then removed.** A device double whose
   `monitorCharacteristicForService` returns a `remove` spy. Run a handshake to completion; assert
   `remove` was called exactly once. Then assert the same on a *failing* handshake (wrong `K_sess`
   → `AUTH_FAILED`) — the `finally` exists precisely so the error path is covered too.
2. **No subscription created — nothing removed, nothing thrown.** Reuse the connect-rejection
   manager from `auth.test.ts:266`. Assert it still resolves to the typed transport outcome and does
   not throw. This pins the ordering constraint the last brief called out: `remove()` must not be
   reached for a subscription that never existed.

**Mutation it must kill:** replace `subscription?.remove();` with a comment. Paste both runs.
