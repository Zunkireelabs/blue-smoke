## 0. Why this exists

While executing `P1-7.0` (2026-08-10, `feature/ble-connectivity`), `npx jest tools/lint-guard`
was found failing 7/7 on the Windows build machine while `gh run list` showed every CI run green.
Tracing the discrepancy surfaced three separate findings, none blocking `P1-7.0` itself but all
worth fixing before `verificationGuard.test.ts` — the proof for inviolable rule 1 — is trusted
again without reservation.

---

## 1. Finding 1 — the 7 local failures are a Windows artefact, not a real break

`tools/lint-guard/__tests__/verificationGuard.test.ts`'s `lintFile()` calls:

```ts
execFileSync('npx', ['eslint', absolutePath, '--format', 'json', ...], { cwd: REPO_ROOT, encoding: 'utf8' });
```

On Windows, `npx` resolves to `npx.cmd`, and `execFileSync` cannot spawn a `.cmd` file without
`shell: true` — it throws `ENOENT` before ESLint ever runs. The surrounding `catch` (see Finding 2)
masks this as "ESLint found nothing," so all 7 tests in the suite fail on an assertion downstream,
not on the spawn itself. `ubuntu-latest` has no `.cmd` resolution problem, so CI has always been
green — confirmed directly against `gh run list`, not inferred. **Not** an ESLint API mismatch:
ESLint is `8.57.1` in this repo, and `--no-eslintrc`/`-c` are the correct flags for that major
version.

Nothing to fix here beyond Finding 2 below — the failure mode itself is expected and already
documented as such in the `P1-7.0` execution brief's §2.

## 2. Finding 2 — the same `catch` is a real defect, on every platform

```ts
} catch (err) {
  const execErr = err as { stdout?: string | Buffer };
  stdout = execErr.stdout ? execErr.stdout.toString() : '[]';
}
```

When the child process never spawns, `err.stdout` is `undefined`, not empty — the fallback to
`'[]'` makes "ESLint did not run" and "ESLint found nothing" the same value. `results[0]` then
reads as `undefined`, which is why the Windows suite fails downstream on `result.errorCount`
rather than failing loudly at the spawn. This is the file guarding inviolable rule 1
(`docs/audits/P2-1.0-retroactive-review.md` finding F1); its own header says a green check that
was never broken is not evidence. On Linux the spawn always succeeds today, so the four
CLEAN-CASE assertions (`errorCount === 0`) currently pass for the right reason — but they would
pass identically, and silently, if a future change broke the spawn there too. That's the actual
risk: **the suite cannot currently tell "ESLint ran and found nothing" apart from "ESLint never
ran," on any platform.**

## 3. Scope

Three independent items. Do all three in one PR — they share the CI-hardening theme but touch
different files, so review them as a numbered list rather than one diff.

### 3.1 Fix `lintFile()`

- Spawn portably: add `shell: true` to the `execFileSync` options. The argv passed to it is
  code-controlled (a fixed `absolutePath` this same test just wrote, plus static flags) — note
  that in a comment next to the option, since `shell: true` is usually a red flag and a reviewer
  should not have to re-derive why it's safe here.
- Replace the `'[]'` fallback with a **throw** when the child process didn't produce output —
  distinguish "spawn failed" from "ESLint ran and reported nothing" at the point where the
  information still exists, rather than losing it to a placeholder.
- **Prove it**: point the spawn at a nonexistent binary (e.g. temporarily swap `'npx'` for a
  bogus command in a throwaway local edit, or inject a broken `PATH` for the child process) and
  confirm the new code throws an explicit, readable error instead of failing downstream on
  `errorCount`. Revert the injection; it's a proof step, not a permanent test double.

### 3.2 `secret-scan` CI job

Add a new job to `.github/workflows/ci.yml`, alongside `promotion-guard` and `verify`:

- `gitleaks/gitleaks-action@v2`.
- Checkout with `fetch-depth: 0` — gitleaks needs full history to scan past commits, not just the
  PR diff.
- A `.gitleaks.toml` allowlisting known decoys **by explicit path**, not by pattern:
  - `.env.example`
  - `debug.keystore`
  - the Supabase **anon** key (wherever it's currently committed as a public, intentional value)
  - 🔴 **Never** an allowlist rule that would also match the **service-role** key — CLAUDE.md's
    "Never commit secrets" rule names the service-role key specifically as the one that bypasses
    every RLS policy. A path-based allowlist entry cannot accidentally widen to catch it; a
    pattern-based one could.
- **Blocking** — no `continue-on-error: true`. A secret-scan job that doesn't fail the build isn't
  a gate, it's a dashboard.
- **Prove it**: on a scratch commit (never pushed, or pushed to a throwaway branch and deleted
  after), plant a fake service-role-shaped JWT and confirm the job fails. Confirm it does *not*
  fail on the legitimate anon key or the other allowlisted paths.

### 3.3 `rls-proofs` CI job

- `supabase start`, then `supabase db reset` to apply migrations against a clean local Postgres.
- Run the existing SQL proofs in `supabase/tests/*.sql` via `psql`, behind a new `test:rls` npm
  script (see the contested-file note below).
- Five proof files exist today: `k_dev_accessor_proof.sql`, `revoke_session_proof.sql`,
  `rls_ownership_proof.sql`, `vault_k_dev_proof.sql`, `verifications_write_denial_proof.sql`.
  🔴 **Never weaken an assertion to make a proof pass.** If one of the five doesn't run cleanly in
  CI (a missing fixture, a seed-data dependency, an ordering assumption that only held when run
  by hand) wire the four that do, and **name the fifth and the specific reason it doesn't run
  yet** in the PR body — don't silently drop it or loosen what it checks to get it green.

⚠️ **Item 3 needs a new `package.json` script** (`test:rls`). `package.json` is a contested file
per `CLAUDE.md` — announce it to Sadin and Hardik before adding the script, the same as any other
dependency/script change to that file. This is a heads-up for whoever executes this brief, not
scope for this document.

## 4. Non-scope — do not absorb

- **Signing, TestFlight, Play Store submission, both-platform release builds.** All gated on 🔴
  **OQ-8**, unrelated to CI correctness.
- **Any change to `verificationGuard.test.ts`'s assertions themselves.** This brief fixes how the
  helper detects ESLint's output, not what the guard checks for.
- **Fixing the 7 Windows-only failures by disabling or skipping them.** Finding 1 says they are
  expected on that platform; the fix in §3.1 makes the *failure mode* correct (a loud spawn error
  instead of a masked one), not the *count* zero on Windows.
