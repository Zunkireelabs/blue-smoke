### The contract (spec §5.4.1, restated in full — do not work from memory)

```
POST /functions/v1/revoke-device-session
Authorization: Bearer <supabase user JWT>
Body: { "session_id": "<hex 16B>" }   // OMIT the field to revoke every active session for the caller

  1. Resolve user_id from the JWT. Reject if absent/expired.
  2. UPDATE device_sessions SET revoked_at = now()
       WHERE session_id = $1 AND user_id = <caller> AND revoked_at is null
  3. Affected 0 rows → 404 { error: "SESSION_NOT_FOUND" }
  4. audit_log: 'session_revoked'
  5. Respond 200 { revoked: <count>, revoked_at: "<iso8601>" }
```

## 3. ⚠️ A spec ambiguity I am resolving here, not leaving to you

Step 3 says "affected 0 rows → 404". That is plainly right for the **single-session** case and
plainly wrong for the **bulk** case: "revoke everything I have" when nothing is active is a
*satisfied* request, not a missing resource. A 404 there would make a correct client look
broken, and would push callers into treating 404 as success — which would then mask the real
single-session 404.

**Implement:**

| Case | Result |
|---|---|
| `session_id` given, 1 row updated | `200 { revoked: 1, revoked_at }` |
| `session_id` given, 0 rows updated | `404 { error: "SESSION_NOT_FOUND" }` |
| `session_id` omitted, N ≥ 1 rows updated | `200 { revoked: N, revoked_at }` |
| **`session_id` omitted, 0 rows updated** | **`200 { revoked: 0, revoked_at }`** ← the deviation |

**Flag this in your report under "Deviations".** I will record it as a spec clarification; you
do not edit `TECHNICAL_SPEC.md`.

Add **`supabase/tests/revoke_session_proof.sql`**, modelled closely on the four existing proof

header documenting two ways a proof can lie, and both apply to you:

1. **`SET LOCAL` is a no-op outside a transaction.** Wrap the whole script in `begin; … rollback;`

2. **Denied `UPDATE` does not raise** — it affects zero rows and returns success. Assert on the

The proof must cover, at minimum:

- User B cannot revoke user A's session (the `user_id` predicate is the *only* authorisation on
  this endpoint — `device_sessions` has no client UPDATE policy at all, so there is no RLS
  backstop if the predicate is wrong).
- A revoked row stays revoked and `revoked_at` does not move on a second attempt (idempotency).
- The bulk predicate updates only the caller's rows when two users both have active sessions.
  Seed A with 2 and B with 1, revoke-all as A, assert B's is untouched and still `revoked_at is null`.

## 7. The traps — enumerated because each one ships silently

### 7.1 🔴 `session_id` is `bytea`, not text. This is the one that will get you.

`issue-device-session` writes it as a **`\x`-prefixed hex literal**:

```ts
session_id: `\\x${toHex(sessionId)}`
```

A query built as `.eq('session_id', sessionIdHex)` — the obvious thing to write — **matches zero
rows, every time.** The endpoint then returns a clean `404 SESSION_NOT_FOUND`, which looks like
correct behaviour for a session that does not exist, and **revocation silently never works.**
Nothing else in the system would look wrong.

Use the same `\x`-prefixed encoding on the way in. Your SQL proof is what confirms it: seed a row
through the *same* representation `issue-device-session` writes, then revoke it and assert
`revoked_at is not null`. A proof that seeds a row some other way proves nothing about this.

### 7.2 🔴 The `user_id` predicate is never optional

It is the entire authorisation model for this endpoint. It must be present in **both** branches —
single and bulk. A bulk revoke that loses it is a cross-user session wipe.

### 7.3 404, never 403, for someone else's session

A session id that exists under a different user must be indistinguishable from one that does not
exist. Returning 403 for the former turns the endpoint into an existence oracle. This falls out
naturally from putting `user_id` in the `WHERE` clause — do not add a "does this exist at all?"
lookup to produce a friendlier error.

### 7.4 Validate the input, do not hand it to the database

- Not a string → `400 INVALID_SESSION_ID`
- Not exactly 32 hex chars → `400 INVALID_SESSION_ID`
- Lowercase it before comparing; `issue-device-session` emits lowercase hex.
- Explicit `null` for `session_id` is **invalid**, not "revoke all". Only an *absent* field means
  bulk. `{"session_id": null}` is far more likely a client bug than a deliberate mass revoke, and
  guessing wrong in that direction logs everyone out.

### 7.5 `audit_log.metadata` carries no identifiers

Spec §5.2.8: metadata must never contain PII. Write `{ revoked_count: n }` and nothing else. The
`user_id` / `device_id` columns exist for identity; do not duplicate ids into the JSON, and do not
put `session_id` in there.

### 7.6 Do not touch `device_ownership`

Revoking a session is not unpairing. §5.4.1 is explicit that revocation does not reach the device
— a device holding a valid `K_sess` honours it until `sessionExpiry` elapses, by design. Do not
"help" by also revoking ownership, and do not add a comment claiming the device is now locked out.

### 7.7 Do not modify anything outside your files

Not `issue-device-session/index.ts`, not `deriveSessionKey.ts`, not the migrations, not
`protocol.ts`. If you believe one of them is wrong, **report it — do not fix it.** The last four
defects on this project were found exactly that way, and one of them (§4.5 frame ordering) was
found because an executor flagged an ambiguity instead of papering over it.
