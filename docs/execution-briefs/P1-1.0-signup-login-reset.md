## 3. Scope — build exactly this

### 3.1 Auth method choice screen

- Single decision point before either flow: "Continue with Email" / "Continue with Phone"
- No default pre-selected; equal visual weight for both — this task does not decide which method
  is "primary," it offers both

### 3.2 Method A — Email + password *(original scope)*

- Signup screen — email + password, Zod validation
- Password strength requirements + inline feedback (do not invent a specific rule set — check for
  one in the spec/brand guidelines first; if genuinely absent, use a documented, defensible
  baseline — e.g. zxcvbn score or NIST 800-63B length-only guidance — and say in your report which
  you picked and why)
- Login screen — errors must not leak whether an account exists (generic "invalid email or
  password" for both "no such account" and "wrong password")
- Password reset request + email flow
- Deep-link handling for the reset link, both platforms (config only — cannot be tested without a
  device, see §2)

### 3.3 Method B — Phone number + OTP *(proposed, spec §1.2.1)*

- Phone input with country-code picker, validated via `libphonenumber-js`
- OTP entry screen — segmented 6-digit input, resend cooldown timer (use the same UX pattern as
  the email flow's "check your email" state, adapted)
- Error handling mirrors Method A — no enumeration, no leaking account existence
- **Do not configure Twilio Verify itself** — that is Supabase dashboard/project configuration,
  which belongs to `P0-3.0`. This task builds the client-side flow against the abstraction in §3.5.

### 3.4 Shared — both methods

- Session persistence — refresh token in Keychain/Keystore (🟠 secret-at-rest, spec §8.1)
- Auto-refresh + graceful expiry handling
- Sign-out clears all local secrets, including any `K_sess` if present
- `profiles` row created on signup, regardless of method
- Account-linking policy (spec §1.2.1): a first-time method with no existing link always creates a
  new account. Linking email + phone to one identity only happens as a deliberate
  already-authenticated action — **do not build an automatic merge at verify time under any
  circumstance**, even as a convenience shortcut
- Email verification flow (if enabled) handled

### 3.5 `AuthClient` abstraction — build this regardless of `P0-3.0`'s status

Because `P0-3.0` may not have landed, screens must not call `@supabase/supabase-js` directly.
Define a typed interface in `src/features/auth/client.ts`:

```ts
interface AuthClient {
  signUpWithEmail(email: string, password: string): Promise<AuthResult>;
  signInWithEmail(email: string, password: string): Promise<AuthResult>;
  requestPasswordReset(email: string): Promise<void>;
  requestPhoneOtp(phone: string): Promise<void>;
  verifyPhoneOtp(phone: string, code: string): Promise<AuthResult>;
  signOut(): Promise<void>;
}
```

- Build screens/hooks against this interface only.
- Provide a mock implementation (`mockAuthClient.ts`) so the flow is demonstrable and unit-testable
  without a live backend.
- Leave a `supabaseAuthClient.ts` stub with correct types and `throw new Error('P0-3.0')` bodies —
  same pattern `P0-4.0` used for `ble/connection.ts` etc. Swapping the mock for the real
  implementation once `P0-3.0` lands should be a one-line change at the composition root.

## 7. Rules that will get this rejected on review

Straight from `CLAUDE.md` and this brief.

1. **A direct `@supabase/supabase-js` call from a screen or hook**, bypassing the `AuthClient`
   interface.
2. **An automatic account merge at OTP/verify time.** Linking is deliberate-and-authenticated only,
   with no exceptions.
3. **`any`, or a non-null `!` on a value crossing a trust boundary** (e.g. a token, a session).
4. **A committed secret** — no Supabase URL/anon key hardcoded outside env config.
5. **Claiming something works without running it.** If a command fails, report it with the output.
6. **Creating a second branch for this task**, or force-pushing `main`.
7. **Presenting Method B as finalized** in user-facing copy, code comments, or the report — it is
   proposed, not confirmed.
8. **Building `P0-3.0` or `P0-4.0` work inside this branch** because they're blocking — flag the
   block instead; scope creep here just relocates the same problem.
