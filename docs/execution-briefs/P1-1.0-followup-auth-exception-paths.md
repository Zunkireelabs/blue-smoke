# Execution brief — P1-1.0 follow-up: the auth screens have no exception path

**Base:** `chore/integrate-auth-db-persona` @ `3369765`
**Scope:** `src/features/auth/**` only.
**Found by:** driving the running app in the simulator, not by reading code or running tests.

## The defect

Every submit handler in `src/features/auth/` follows this shape:

```ts
setStatus('submitting');
const result = await authClient.requestPhoneOtp(e164.data);
setStatus('idle');                    // ← never runs if the await REJECTS
if (!result.ok) { setFormError(result.error); return; }
```

If the awaited call **throws** rather than returning `{ok:false}`, `setStatus('idle')` is skipped,
`onSubmit`'s promise rejects unhandled, and the screen is left permanently in `submitting`:
spinner spinning, button disabled, input non-editable, **no message to the user, no way back
except killing the app.**

Observed live in the simulator: `Uncaught (in promise, id: 0): "Error: SUPAB…"` with the submit
button stuck in its loading state.

**All six screens are affected** — `LoginScreen`, `SignupScreen`, `OtpEntryScreen`,
`PhoneInputScreen`, `PasswordResetRequestScreen`, `ResetPasswordConfirmScreen`. Each contains
`setStatus('submitting')` and **zero `try` blocks**.

This fails the Definition of Done: *"Error states have a user-visible recovery path."*

## Root cause — fix this first, it is the single point

`src/features/auth/supabaseAuthClient.ts` declares `Promise<AuthResult>`, a Result type whose
whole purpose is that failures come back as values. But every method calls `getSupabaseClient()`
**outside any try**, and that function throws by design when config is missing:

```ts
async requestPhoneOtp(phone): Promise<AuthResult> {
  const supabase = getSupabaseClient();          // ← throws; escapes the Result contract
  const { error } = await supabase.auth.signInWithOtp({ phone });
  if (error) return { ok: false, error: error.message };
  return { ok: true, data: undefined };
}
```

Make every `supabaseAuthClient` method honour its own signature: wrap the whole body so **no path
throws**, and return `{ ok: false, error: <user-facing message> }` instead.

The message must be **coaching, not diagnostic** (CLAUDE.md). "We couldn't reach the server. Check
your connection and try again." — never a stack trace, never a raw SDK string for an internal
fault, never anything naming Supabase.

## Then: defence in depth in the screens

Even with the client fixed, no screen should be able to strand itself. In each of the six, wrap
the async section so the status reset runs on the exception path too:

```ts
try {
  const result = await authClient.<method>(...);
  if (!result.ok) { setFormError(result.error); return; }
  navigation.navigate(...);
} catch {
  setFormError('Something went wrong. Please try again.');
} finally {
  setStatus('idle');
}
```

`finally` is the point — same discipline as CLAUDE.md's "zeroise in `finally`, so it runs on the
exception path too". Do not swap it for a `.catch()` that forgets to reset status.

Keep each screen's existing early-return validation exactly as it is. **That path already works** —
verified in the simulator: submitting an empty phone field renders "Enter a valid phone number for
the selected country." and leaves the button usable. Do not restructure it.

## Tests

`mockAuthClient` currently only models the success/`{ok:false}` shapes. Add a way to make a method
**throw**, then assert per screen:

1. On a thrown error the screen shows a user-visible message.
2. On a thrown error the submit control returns to enabled — **assert the resolved `disabled`
   prop / loading state**, not merely that the component still renders.
3. The existing validation-error path is unchanged.

Assertion 2 is the one that actually encodes this bug. A test that only checks "some error text
appears" passes against a screen that is still bricked.

## Do not

- Do not "fix" this by making `getSupabaseClient()` return null instead of throwing. Throwing on
  absent config is correct — it is loud at the boundary. The bug is that nothing catches it.
- Do not add a global unhandled-rejection handler as the fix. That hides the symptom and leaves
  every screen still stuck.
- Do not touch `src/shared/lib/supabaseClient.ts`.
