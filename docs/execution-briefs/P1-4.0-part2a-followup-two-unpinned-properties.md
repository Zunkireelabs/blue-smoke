## 3. Finding 9 🟠 — the exact-length check is only half tested; over-length data parses

### What is wrong

`deviceInfo.ts` — the length guard inside `readDeviceInfo()`:

```ts
if (bytes.length !== CHARACTERISTIC_LENGTH_BYTES.deviceInfo) {
```

Weakening `!==` to `<`: **10 passed, 0 failed.** Nothing in the suite holds the upper bound.

The suite has exactly one wrong-length fixture and it is 5 bytes — *under* length. So the test
proves the guard rejects short reads and says nothing about long ones. §4.2 specifies `deviceInfo`
as **exactly 20 bytes** (C1), not "at least 20".

### Why it matters here specifically

This is not a hypothetical. **The over-length read is precisely what a firmware that extends the
characteristic would produce** — a v2 that appends fields, or that spends the two `reserved` bytes
at offset 18 and grows past them. And `readDeviceInfo()` is *the* function whose entire job is
detecting that we are talking to a device we may not understand. A parser that silently accepts a
24-byte `deviceInfo` would report `compatible: true` off the first byte while ignoring that the
device's layout has moved underneath it — which is the exact failure the `protocolVersion` check
exists to catch, arriving through the door the length check was supposed to hold shut.

### The fix — one test

Add an **over-length** fixture alongside the existing 5-byte one. Build a valid 20-byte buffer with
`buildDeviceInfoBytes` and append one trailing byte (21 total) — an over-length buffer whose first
20 bytes are otherwise perfectly parseable, so the *only* thing that can reject it is the length
check itself. Assert the typed transport outcome and its exact detail string
(`deviceInfo: expected 20 bytes, got 21`).

Prefer `test.each` over a copy-pasted third test if it reads cleanly against the existing
under-length case; either is acceptable.

**Mutation it must kill:** change `bytes.length !== CHARACTERISTIC_LENGTH_BYTES.deviceInfo` to
`bytes.length < CHARACTERISTIC_LENGTH_BYTES.deviceInfo`. Paste both runs.

## 4. Finding 10 🟡 — two fixtures violate the distinct-byte rule, and a mutation survives on luck

### What is wrong

`protocolVersion` and `provisioningState` hold **the same value** in both main fixtures:

| Fixture | `protocolVersion` | `provisioningState` | Collides? |
|---|---|---|---|
| mock-driven (`buildMockPeripheral()`) | `1` (`PROTOCOL_VERSION`) | `1` (`PROVISIONED`, the mock default) | **yes** |
| mismatch (`buildDeviceInfoBytes`) | `2` (`PROTOCOL_VERSION + 1`) | `2` (`ACTIVATED`) | **yes** |
| out-of-range | `1` | `3` (invalid) | no |

Swapping the two offsets in `parseDeviceInfo` **is** killed today — but only by the third fixture,
which happens to use `3` because it is testing something else entirely. Neither test that actually
asserts these two fields can tell the offsets apart. Change the out-of-range fixture's unrelated
sentinel value at any point in the future and the mutation goes green.

The Part 2a brief's §5 fixture rule is that a repeated byte cannot distinguish a wrong offset from
a right one. That rule was applied carefully to `deviceUid`, `hwRevision`, `fwVersion` and
`keyGeneration` — the report's §2 claim that "every scalar is distinct" is simply not true once
`provisioningState` is included, and this is what it cost. Deliberate, not lucky, is the standard.

### The fix — no new test, two fixture edits

1. **Mock-driven fixture:** build the peripheral with `ProvisioningState.ACTIVATED` (`2`) so it
   differs from `PROTOCOL_VERSION` (`1`), and update that test's assertion to match. Do **not** use
   `UNPROVISIONED` — `0` is the value a zeroed buffer produces, which reintroduces a different
   blind spot.
2. **Mismatch fixture:** its `protocolVersion` is `2`, so give it `ProvisioningState.PROVISIONED`
   (`1`), and assert `provisioningState` explicitly in that test — it currently asserts
   `hwRevision`, `fwVersion` and `keyGeneration` but never this field.

Leave the `test.each` block that round-trips all three provisioning states alone. It is correct and
it is what proves the field is read at all.

**Mutation it must kill:** swap the offsets used for `protocolVersion` and `provisioningState` in
`parseDeviceInfo`. **The acceptance bar is specific:** the *field-by-field* test **and** the
*mismatch* test must each fail on their own. It is not sufficient that the suite goes red — the
out-of-range test already does that, and that is the accident being removed. Paste the run and show
which test names failed.

## 5. Deliberately not in scope

**The `READ_TIMEOUT_MS` value is not pinned, and that is accepted.** Changing `3000` to `1500`
leaves 10/10 green, because the hung-read test advances fake timers by exactly `3000`, which fires
any budget at or below it. **Do not fix this.** That the read times out *at all* is already pinned
(the Part 2a brief's mutation 6 kills the `withTimeout` passthrough), and `3000` is an app-level
operational choice, not a §4 constant — pinning it to the millisecond would test a number nobody has
ruled on. It is recorded here so it is not re-discovered and "fixed" with a brittle test.

**Also not in scope:** the shared-base64 extraction (`a328da6`'s report finding 3). It is real —
`base64ToBytes` is duplicated byte-for-byte from `auth.ts`, and both copies use `indexOf`, which
returns `-1` for an invalid base64 character and yields silent garbage rather than an error. That
touches `auth.ts`, which is a production change and a wider blast radius than this brief. It waits
for the module that needs base64 third.

**Still out of scope from `P1-4.0-bonding-seam-and-handshake.md` §7:** `serial_hash` and its salt
(🔴 **OQ-12** — a guessed value fails *silently*), `issue-device-session` wiring, Keychain `K_sess`,
the pairing screen, LESC bonding. **Do not tick any P1-4.0 checkbox in `TODO-phase-1.md`** — the
task stays 3/12 until the whole of it lands.

**Do not invent `protocolVersion`-mismatch policy.** `readDeviceInfo()` deliberately reports
`compatible: false` as a fact and decides nothing. §4.3 defines a version-bump process but never
client behaviour; that belongs to **OQ-6**, is registered in spec §13, and is explicitly *not*
blocking. Adding a refusal, a disconnect, or a routing decision here will get the diff rejected.
