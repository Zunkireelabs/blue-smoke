## 1. Context you do not have

### 1.1 The authority model is the whole point, and it makes this spike *safe to fail*

§7.1 splits responsibility:

| Layer | Role | Authority |
|---|---|---|
| Firmware dead-man timer (§4.8 **F2**) | Locks `autoLockGraceMs` after any disconnect | **AUTHORITATIVE** |
| App proximity monitor (§7.2) | Issues an explicit `LOCK` on RSSI degradation, before disconnect | **ADVISORY** |

So every background failure mode — OS kills the app, user force-quits, battery dies, OEM murders the
process — **degrades to "the device locks itself."** That is the safe direction, and it is why we can
ship without guaranteed background operation.

**The consequence for you is a licence to report bad news.** You are not looking for a way to make
background BLE work. You are looking for **the truth about what each platform actually guarantees**,
so the client-facing claim matches reality. A spike that concludes "far less works than we assumed"
is a *successful* spike. Do not engineer around a limitation — document it.

### 1.2 ⚠️ The question this spike now exists to answer — read this before scoping your time

While scoping this brief I found what looks like a **collision between §7.4 and §8.1 that neither
section can see on its own.** It is unconfirmed. **Confirming or refuting it is now this spike's
highest-value output** — above the manifest work, above everything else.

The reasoning, so you can attack it rather than inherit it:

1. §4.6 `lockCommand` is an **authenticated write**. Its tag is `AES-CMAC(K_sess, N ‖ bytes[0..11])`.
   **Sending a `LOCK` therefore requires `K_sess`.**
2. §8.1 classifies `K_sess` 🟠 secret-at-rest and mandates iOS Keychain
   **`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`**, hardware-backed, **biometric-gated where
   available**. §8.3 reinforces it: the "stolen phone" mitigation *is* the biometric gate.
3. A `WhenUnlockedThisDeviceOnly` item is **unreadable while the phone's screen is locked.** A
   biometric-gated item is **unreadable without user presence**, therefore unreadable in *any*
   background execution context.
4. `K_sess` held **in RAM** survives ordinary backgrounding. It does **not** survive process death.
5. **Every background recovery path §7.4 describes is a process-death path** — iOS state restoration
   via `CBCentralManagerOptionRestoreIdentifierKey` relaunches a *fresh process*; an Android
   foreground service restarted after an OEM kill is a *fresh process*.

If 1–5 hold, then on exactly those paths the app can reconnect and **read** `lockState`, but cannot
**derive a valid tag**, so it cannot issue the advisory `LOCK` at all. And the primary use case —
**phone in a pocket, screen locked, user walks away** — is precisely the case where the Keychain item
is unreadable.

**This is not a safety defect.** §7.1 means the firmware still locks the device. It is a **capability
defect**, and it falsifies specific claims we are close to making:

- §7.4's "the app makes it lock faster when it is running" — *running* is doing a lot of work in that
  sentence, and it may be false whenever it matters most.
- `P3-4.0`'s boxes "iOS: proximity monitoring continues in background" (monitoring, perhaps — but not
  *acting*) and "iOS: reconnect-and-re-handshake works after a background relaunch" (the handshake
  needs `K_sess`).
- Most of `P3-3.0`'s RSSI hysteresis work, whose value drops sharply if it only ever runs in the
  foreground.

**There is a fix, and it is a security decision, not an engineering one:** store `K_sess` under
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` **without** a biometric gate (keeping the gate on
the Supabase refresh token and on privileged UI actions). That buys background capability by
surrendering the §8.3 stolen-phone mitigation, and it would need writing into §8.5 as an accepted
residual risk.

**Your job is to establish the facts, not to pick.** Specifically:

- Confirm or refute (3) against Apple's Keychain documentation, naming the accessibility constants and
  the exact conditions under which each is readable.
- Establish the Android equivalent: whether an Android Keystore key with `setUserAuthenticationRequired(true)`
  is usable from a foreground service while the device is locked.
- Determine what `react-native-keychain` ^10 actually exposes for both, since that is what is in
  `package.json`.
- **State plainly whether the app can send an authenticated `LOCK` in each background scenario**, in
  the capability matrix (§3.3).

Then **stop and report.** Do not edit §8.1. Do not implement a storage strategy. The choice between
"background capability" and "stolen-phone mitigation" belongs to `P0-6.0` and to the client.

> This would be the twelfth defect found by re-deriving a section instead of trusting it, and the
> first that spans three sections — §7.4, §8.1 and §8.3 are each internally consistent, which is
> exactly why it survived two audits. **If you think the reasoning above is wrong, say so with the
> citation that kills it.** That is a completely acceptable outcome and a fast one.

### 1.3 The background configuration does not exist yet — none of it

`P0-4.0` scaffolded the app and wired `react-native-ble-plx`, but **nothing about background

| File | Present | Missing |

  module. `package.json` is a `CLAUDE.md`-contested shared file: **do not add a dependency in this

### 3.2 The state-restoration contract — a document, not code

Write down what `P1-4.0` must implement in `connection.ts`, precisely enough to be implemented from:

- What `react-native-ble-plx` ^3.5.1 exposes for iOS restoration (`restoreStateIdentifier`,
  `restoreStateFunction`) and what it hands back on relaunch.
- **What state the app has and has not got at that moment** — and per §1.2, whether `K_sess` is among
  it. This is the crux.
- Whether a restored connection must re-run the §4.5 handshake, and **what happens if it cannot.**
  Note §4.8 **F3**: reconnecting without a successful handshake does *not* cancel the dead-man
  countdown. So a restored-but-unauthenticated app is, from the device's point of view, indistinguishable
  from no app at all. Follow that through and state what the user actually experiences.
- The §7.3 state the app should occupy after restoration. The §7.3 invariant is absolute: `UNLOCKED`
  is reachable **only** through `AUTHENTICATED` + activated + explicit user action. **A restoration
  path must never resume `UNLOCKED`.** If your reading of restoration suggests otherwise, that is a
  finding — report it, do not code around it.

### 3.3 The honest capability matrix — the actual deliverable

This is what goes to the client. §7.4 already commits us to the shape of the claim: *"the device
always locks when the phone goes away, regardless of app state, and the app makes it lock faster when

One row per scenario, one column per platform, and for each cell state **(a)** does the app keep the
connection, **(b)** can it still send an authenticated `LOCK` (§1.2), **(c)** does the device still
lock regardless — and **(d)** is this *guaranteed* or *best-effort*, with the citation.

Minimum scenarios — these are `P3-4.0`'s boxes, so use its language:

| Scenario |
|---|
| App foregrounded |
| App backgrounded, screen on |
| **App backgrounded, screen locked, phone in pocket** ← the primary use case |
| App evicted by the OS, then restored (iOS) / FGS restarted (Android) |
| **User force-quits the app** |
| Phone powered off |
| Airplane mode / Bluetooth disabled |

Every cell is **derived from documentation and marked unverified**, since nothing can be measured

than no matrix, because it will be read as evidence.

Column (c) should be `yes` in every single row, on both platforms, by §4.8 F2 — **and if you find a
row where it is not, stop immediately and report it.** That would be a safety finding, not a
